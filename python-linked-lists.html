Linked Lists
Nodes, pointers, and the cost of lookup

A complete, practical guide to linked lists in Python — how to build them from scratch with classes, how traversal and insertion actually work, and why they trade random access for cheap insertion.

⛓️ Why Linked Lists Exist

Arrays are fast to index and slow to insert — linked lists flip that

The Core Trade-Off

A Python list is a contiguous array. Getting the item at index i is a single arithmetic step and a memory read, so it's O(1). But inserting at the front requires shifting every existing element one slot to the right, which is O(n). That's the trade: fast access, expensive insertion.

A linked list inverts it. Each element is a separate node holding a value and a pointer to the next node. There is no contiguous block, so there is no shifting — inserting at the front is just a couple of pointer assignments, O(1). But finding the item at index i means walking from the head through i pointers, which is O(n). That's the trade: expensive access, cheap insertion.

In everyday Python you'll almost always reach for a list or a deque. Linked lists matter when you're building other structures on top of them — stacks, queues, hash tables with chaining, LRU caches, and graph adjacency lists all rely on the same node-and-pointer idea. Learning to build one is learning the vocabulary.

Python has no built-in linked list

The closest standard option is collections.deque, which is implemented as a doubly-linked list of blocks internally. Building one from scratch with classes is the clearest way to understand the mechanics.

🔵 The Node — The Only Building Block

One class, two attributes

A node holds one value and one reference to the next node. That's the whole idea. A linked list is just a chain of these, with a head variable pointing to the first one and the last node's next set to None.

node_basics.py 
class Node:
    def __init__(self, value, next=None):
        self.value = value
        self.next = next

    def __repr__(self):
        return f"Node({self.value!r})"

n1 = Node("a")
n2 = Node("b")
n3 = Node("c")

n1.next = n2
n2.next = n3

print(n1)                 # Node('a')
print(n1.next)            # Node('b')
print(n1.next.next)       # Node('c')
print(n1.next.next.next)  # None
The last node's next is None. That None is what signals the end of the list. Every traversal loop terminates when it hits it, which is why None is sometimes called the list's "sentinel".

Traversal

traverse.py 
class Node:
    def __init__(self, value, next=None):
        self.value = value
        self.next = next

head = Node(1, Node(2, Node(3, Node(4))))

def to_list(head):
    result = []
    node = head
    while node is not None:
        result.append(node.value)
        node = node.next
    return result

print(to_list(head))      # [1, 2, 3, 4]

# Count nodes
def length(head):
    count = 0
    node = head
    while node:
        count += 1
        node = node.next
    return count

print(length(head))      # 4

The traversal pattern is always the same: start with a pointer at the head, do something with the current node, then move the pointer forward. The loop stops when the pointer becomes None.

➡️ A Singly-Linked List Class

Wrap the nodes in a list object

A LinkedList class holds a reference to the head node and provides methods for the common operations. This is the standard way to package the mechanics into something usable.

singly_list.py 
class Node:
    def __init__(self, value, next=None):
        self.value = value
        self.next = next

class LinkedList:
    def __init__(self):
        self.head = None
        self._size = 0

    def append(self, value):
        new = Node(value)
        if self.head is None:
            self.head = new
        else:
            node = self.head
            while node.next:
                node = node.next
            node.next = new
        self._size += 1

    def prepend(self, value):
        self.head = Node(value, self.head)
        self._size += 1

    def to_list(self):
        result = []
        node = self.head
        while node:
            result.append(node.value)
            node = node.next
        return result

    def __len__(self):
        return self._size

    def __iter__(self):
        node = self.head
        while node:
            yield node.value
            node = node.next

ll = LinkedList()
ll.append(1)
ll.append(2)
ll.append(3)
ll.prepend(0)

print(ll.to_list())      # [0, 1, 2, 3]
print(len(ll))         # 4
print(list(ll))        # [0, 1, 2, 3]
Two different costs inside one class. prepend() is O(1) — it just creates a node and points it at the current head. append() is O(n) — it has to walk to the end of the list first. That asymmetry is the point of a linked list: cheap at the head, expensive at the tail, unless you store a tail reference.

Adding a tail reference for O(1) append

class LinkedList:
    def __init__(self):
        self.head = None
        self.tail = None     # remember the last node
        self._size = 0

    def append(self, value):
        new = Node(value)
        if self.head is None:
            self.head = self.tail = new
        else:
            self.tail.next = new
            self.tail = new
        self._size += 1
    # Now append is O(1) instead of O(n)

A tail pointer is one of the most common optimizations to a linked list. It turns append() from O(n) to O(1), at the cost of one extra reference and a bit of bookkeeping when you delete the last node.

⚙️ Insertion, Deletion, and Search

Pointer surgery — the tricky part

Insertion and deletion are all about the pointers around the target. Get those right and the node drops in or out cleanly; get them wrong and you either lose the rest of the list or create a cycle.

Insert at the head — O(1)

def prepend(self, value):
    new = Node(value, self.head)   # new points at old head
    self.head = new                # head now points at new
    self._size += 1

# Before:  head -> A -> B -> None
# After:   head -> X -> A -> B -> None

Insert after a specific node — O(1) once you have the node

def insert_after(self, target, value):
    if target is None:
        raise ValueError("target node is None")
    new = Node(value, target.next)  # new points at target's successor
    target.next = new               # target now points at new
    self._size += 1

# Before:  A -> B -> C
#           target = B
# After:   A -> B -> X -> C
The order matters. Set new.next to target.next before you reassign target.next. If you reverse the two lines, target.next is already pointing at the new node, and you've lost the rest of the list.

Delete a node by value — O(n)

delete.py 
def delete(self, value):
    if self.head is None:
        return False

    if self.head.value == value:
        self.head = self.head.next
        self._size -= 1
        return True

    prev = self.head
    node = self.head.next
    while node:
        if node.value == value:
            prev.next = node.next
            self._size -= 1
            return True
        prev = node
        node = node.next
    return False

# Need to track the PREVIOUS node so it can skip over the target.

Deleting a node means making its predecessor point at its successor. That's why you need two pointers: prev and node.

Search — O(n)

def find(self, value):
    node = self.head
    index = 0
    while node:
        if node.value == value:
            return index, node
        node = node.next
        index += 1
    return -1, None

# Returns (index, node) so callers can chain into insert_after().

There's no shortcut to finding a value in a linked list — every lookup is a full scan. That's the cost of giving up contiguous memory.

The two classic pointer bugs

BugSymptomFix
Reassigning next before reading itLost tail of the listSave the next pointer in a variable first
Creating a cycle by accidentTraversal never endsCheck pointer assignment order; use id() to debug

If a traversal hangs, add a counter that aborts after, say, 100,000 steps and print the values seen so far. That immediately reveals whether the list is cyclic and where the cycle begins.

↔️ Doubly-Linked Lists

Two pointers per node, both directions cheap

A doubly-linked list adds a prev pointer to every node. Now you can walk backwards as easily as forwards, and deleting a node no longer requires scanning from the head to find its predecessor — the node already knows it.

doubly_list.py 
class DNode:
    def __init__(self, value, prev=None, next=None):
        self.value = value
        self.prev = prev
        self.next = next

class DoublyLinkedList:
    def __init__(self):
        self.head = None
        self.tail = None
        self._size = 0

    def append(self, value):
        new = DNode(value, prev=self.tail)
        if self.tail:
            self.tail.next = new
        else:
            self.head = new
        self.tail = new
        self._size += 1

    def prepend(self, value):
        new = DNode(value, next=self.head)
        if self.head:
            self.head.prev = new
        else:
            self.tail = new
        self.head = new
        self._size += 1

    def forward(self):
        node = self.head
        while node:
            yield node.value
            node = node.next

    def backward(self):
        node = self.tail
        while node:
            yield node.value
            node = node.prev

dll = DoublyLinkedList()
dll.append(1)
dll.append(2)
dll.prepend(0)

print(list(dll.forward()))    # [0, 1, 2]
print(list(dll.backward()))   # [2, 1, 0]
OperationSinglyDoubly
Insert at headO(1)O(1)
Insert at tail (with tail pointer)O(1)O(1)
Delete a given nodeO(n)O(1)
Traverse forwardO(n)O(n)
Traverse backwardO(n)O(n)
Memory per node1 pointer2 pointers
The real win is deletion. Given a node in a doubly-linked list, you can unlink it in O(1): node.prev.next = node.next and node.next.prev = node.prev. A singly-linked list has to walk from the head to find the predecessor first. That's why LRU caches — which delete entries constantly — use doubly-linked lists.
Every operation must update both pointers. Forgetting to set new.prev or to update the old head's prev reference leaves the list in a state where forward traversal works but backward traversal breaks. Test both directions.

🔄 Reversing a Singly-Linked List

The classic interview problem, explained properly

Reversing a linked list is three pointer assignments in a loop. The trick is to remember the next node before you change the current node's pointer — otherwise you lose the rest of the list.

reverse.py 
class Node:
    def __init__(self, value, next=None):
        self.value = value
        self.next = next

def reverse(head):
    prev = None
    current = head
    while current:
        nxt = current.next       # 1. remember the rest of the list
        current.next = prev      # 2. flip this node's pointer backward
        prev = current           # 3. advance prev
        current = nxt            # 4. advance current
    return prev                  # prev is the new head

head = Node(1, Node(2, Node(3, Node(4))))

def to_list(head):
    out = []
    while head:
        out.append(head.value)
        head = head.next
    return out

print("before:", to_list(head))   # [1, 2, 3, 4]
head = reverse(head)
print("after: ", to_list(head))   # [4, 3, 2, 1]

Step by step

Start:     prev=None   current=1 -> 2 -> 3 -> 4 -> None

Step 1:    nxt=2
           current.next = prev     (1 -> None)
           prev = 1
           current = 2

State:     prev=1 -> None   current=2 -> 3 -> 4 -> None

Step 2:    nxt=3
           current.next = prev     (2 -> 1 -> None)
           prev = 2
           current = 3

State:     prev=2 -> 1 -> None   current=3 -> 4 -> None

...and so on until current is None, at which point prev is the new head.
Three pointers, four steps. prev, current, and nxt. The loop body always does the same thing: save nxt, flip current.next, advance prev, advance current. Once you see that rhythm, the problem becomes mechanical.

Recursive version

def reverse_recursive(head):
    if head is None or head.next is None:
        return head
    new_head = reverse_recursive(head.next)
    head.next.next = head
    head.next = None
    return new_head

# Elegant, but uses O(n) stack space.
# For very long lists, the iterative version is safer.

The recursive version reads more clearly but uses O(n) stack frames. The iterative version is O(1) space. Both are O(n) time.

⚖️ Linked List vs Python List

When each one wins

OperationlistLinked List
Access by indexO(1)O(n)
Insert at frontO(n)O(1)
Insert at endO(1) amortizedO(1) with tail pointer
Delete at frontO(n)O(1)
Delete a given nodeO(n)O(n) singly, O(1) doubly
Search by valueO(n)O(n)
Memory overheadLowHigh (one or two pointers per node)

When linked lists are the right choice

  • You insert and delete at the head constantly
  • You're building another structure — a stack, a queue, a hash table, an LRU cache
  • Nodes arrive out of order and need to be linked as they come
  • The collection might grow or shrink dramatically at the front

When to use a Python list instead

  • You need random access by index
  • You're iterating more than modifying
  • You're processing numerical data — contiguous memory is much friendlier to the CPU cache
  • You don't have a reason to build a custom structure
In real Python code, list or deque almost always beats a hand-rolled linked list — the C implementation is far faster, and the memory overhead of Python objects makes the pointer nodes unusually expensive. Use linked lists to learn, and when the problem genuinely needs them.

🏗️ Mini Project — An LRU Cache

Put nodes and pointers to work

An LRU (least-recently-used) cache evicts the entry that hasn't been touched for the longest. The classic implementation combines a dictionary with a doubly-linked list: the dict gives O(1) lookup, and the list gives O(1) reordering.

lru_cache.py 
class Node:
    def __init__(self, key=None, value=None):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.cache = {}
        # Sentinel nodes make edge cases disappear
        self.head = Node()
        self.tail = Node()
        self.head.next = self.tail
        self.tail.prev = self.head

    def _unlink(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _push_front(self, node):
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key):
        if key not in self.cache:
            return None
        node = self.cache[key]
        self._unlink(node)
        self._push_front(node)
        return node.value

    def put(self, key, value):
        if key in self.cache:
            self._unlink(self.cache[key])
        node = Node(key, value)
        self.cache[key] = node
        self._push_front(node)
        if len(self.cache) > self.capacity:
            lru = self.tail.prev
            self._unlink(lru)
            del self.cache[lru.key]

    def keys(self):
        result = []
        node = self.head.next
        while node is not self.tail:
            result.append(node.key)
            node = node.next
        return result

cache = LRUCache(3)
cache.put("a", 1)
cache.put("b", 2)
cache.put("c", 3)
print(cache.keys())     # ['c', 'b', 'a']

cache.get("a")
print(cache.keys())     # ['a', 'c', 'b']

cache.put("d", 4)      # evicts 'b' (least recently used)
print(cache.keys())     # ['d', 'a', 'c']

The design decision worth noticing is the use of two sentinel nodes — head and tail — that hold no data. They eliminate every "is this the first or last node?" special case, so _unlink and _push_front never need to check for None. This is the standard trick in production linked-list code.

Every operation here is O(1). The dict handles lookup in constant time; the linked list handles reordering and eviction in constant time. The whole structure exists because no single built-in Python type gives both — which is exactly when a hand-rolled linked list is worth it.
