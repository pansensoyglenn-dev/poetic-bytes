01 — Core Concepts

The Duplication Problem

Without inheritance, you'd write nearly identical classes for each menu category:

❌

Without Inheritance — Duplicated Code

class Appetizer: def __init__(self, name, price, description, serving_size): self.name = name self.price = price self.description = description self.serving_size = serving_size def get_price(self): return self.price def prepare(self): return "Preparing appetizer..." class MainCourse: Same __init__, same get_price, same structure class Dessert: Same __init__, same get_price, same structure

⚠️ The Problem: The __init__ and get_price() logic is duplicated. If you need to add a new attribute (like calories), you must update it in three places. This violates the DRY (Don't Repeat Yourself) principle.

The Solution: Inheritance

✓

With Inheritance — Clean, DRY Code

class MenuItem: def __init__(self, name, price, description): self.name = name self.price = price self.description = description def get_price(self): return self.price def prepare(self): raise NotImplementedError() class Appetizer(MenuItem): def __init__(self, name, price, description, serving_size): super().__init__(name, price, description) self.serving_size = serving_size def prepare(self): return f"Preparing {self.name}..."

✅ Result: The duplication is gone. All menu items share the same base structure. If you add a new common attribute, you add it once in the base class.

🔑 Key Concept: The Open/Closed Principle

The MenuItem base class is open for extension (you can add new menu categories) but closed for modification (you don't need to change existing code). This is one of the SOLID principles of object-oriented design.

The Liskov Substitution Principle (LSP)

LSP states that objects of a superclass should be replaceable with objects of a subclass without affecting the correctness of the program.

❌ Breaking LSP — Bad Example:

class BrokenMainCourse(MainCourse): def get_price(self) -> float: if self.cooking_time > 30: raise ValueError("This dish takes too long!") return super().get_price()

If code expects MainCourse and calls get_price(), it will fail unexpectedly for this subclass. This violates LSP.

✅ Following LSP — Good Example:

class GoodMainCourse(MainCourse): def get_price(self) -> float: if self.cooking_time > 30: return super().get_price() + 5.00 return super().get_price()

This subclass extends behavior without breaking the contract. It still returns a float and works wherever MainCourse is expected.

Inheritance vs Composition

A ComboMeal is not a type of MenuItem — it has menu items. This is composition, and it's often the better choice.

Inheritance ("is-a")

"A MainCourse is a MenuItem"

  • Use for specialization
  • Changes to parent affect children
  • Can lead to deep hierarchies

Composition ("has-a")

"A ComboMeal has MenuItem objects"

  • Use for containment
  • Changes are isolated
  • More flexible and testable

💡 When to use which: Use inheritance when you have a clear "is-a" relationship and you want to reuse behavior. Use composition when you have a "has-a" relationship or when you want to avoid tight coupling. In modern Python, many developers prefer composition + protocols over deep inheritance.

05 — Common Mistakes & Anti-Patterns

What to Avoid

MistakeWhy It's BadBetter Approach
Forgetting super().__init__() Parent attributes are never initialized Always call super().__init__() first
Deep inheritance (5+ levels) Hard to maintain, fragile Prefer shallow hierarchies + composition
Raising exceptions in overridden methods Breaks LSP, violates the contract Extend behavior, don't restrict it
Base class knows about subclasses Violates Open/Closed Principle Keep base class generic
Overriding to change a tiny detail Adds unnecessary complexity Use parameters or composition
Mutable defaults in __init__ Shared state across instances Use None and create fresh objects
