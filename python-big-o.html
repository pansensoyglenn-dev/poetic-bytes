Big-O & Complexity
Measure how code scales

A complete, practical guide to Big-O notation in Python — how to read it, how to derive it from real code, and how to use it to pick the right data structure before performance becomes a problem.

Start with the notation Jump to the complexity table
complexity.py
def find_duplicates(items):
    seen = set()          # O(1) membership
    duplicates = []
    for item in items:     # O(n) loop
        if item in seen:      # O(1) lookup
            duplicates.append(item)
        seen.add(item)        # O(1) insert
    return duplicates
# Overall: O(n) time, O(n) space
$ python complexity.py
[3, 1]
# 1000 items: ~1 ms · 1,000,000 items: ~1 s

📈 Why Big-O Matters

It predicts how code behaves as inputs grow — before you ship it

Complexity Is About Growth, Not Speed

Big-O notation describes how the cost of an algorithm grows as the input size grows. It doesn't tell you how many milliseconds a function takes — it tells you whether doubling the input doubles the time, quadruples it, or barely changes it at all.

That distinction matters because small inputs hide bad algorithms. A quadratic function that runs in a millisecond on 100 items takes 100 seconds on 10,000 items. You may not notice the problem during development and discover it only when real data arrives.

The practical payoff is choosing the right data structure before you write the code. Knowing that a list lookup is O(n) and a set lookup is O(1) is often the difference between a fast program and a slow one — and it requires no profiling at all, because the answer follows from the structure of the code.

Big-O is an upper bound

Formally, O(f(n)) means "grows no faster than f(n)" — it's a ceiling, not an exact count. Two functions that are both O(n) can differ by a constant factor of 100x. Big-O tells you what happens when the input gets large, not how fast a specific run will be.

🔤 Reading the Notation

What O(1), O(n), and O(n²) actually mean

Big-O describes the shape of the growth curve. The letter n stands for the size of the input — the number of items in a list, the number of characters in a string, the number of nodes in a graph. The expression inside the parentheses says how cost scales with that size.

NotationNameWhat it means
O(1)ConstantCost doesn't change with input size
O(log n)LogarithmicCost grows slowly — each step halves the problem
O(n)LinearCost scales directly with input size
O(n log n)LinearithmicSlightly worse than linear — typical of good sorting
O(n²)QuadraticCost scales with the square — nested loops
O(2ⁿ)ExponentialCost doubles with each added input — intractable
O(n!)FactorialCombinatorial explosion — brute-force permutations

How the curves compare

n = 10         n = 100          n = 1,000
─────────────────────────────────────────────────────
O(1)       1             1                1
O(log n)   3             7                10
O(n)       10            100              1,000
O(n log n) 33            664              9,966
O(n²)      100           10,000           1,000,000
O(2ⁿ)      1,024         10³⁰             impractical
Look at the last column. At n = 1,000, the difference between O(n) and O(n²) is a factor of 1,000. At n = 1,000,000 it's a factor of a million. That's why complexity matters: the gap widens as inputs grow.

Dropping constants

Big-O ignores constant factors and lower-order terms. Both of the functions below are O(n), even though one does three operations per item and the other does one:

def one_operation_per_item(items):
    total = 0
    for item in items:
        total += item
    return total
# O(n) — one pass

def three_operations_per_item(items):
    total = 0
    for item in items:
        total += item
        total += 1
        total += 2
    return total
# Also O(n) — constant factor of 3x, but same growth shape

Dropping constants doesn't mean they don't matter in practice — a 3x difference is real. It means they don't change the shape of the curve, and Big-O is about shape.

Keeping only the dominant term

def mixed_complexity(items):
    for item in items:        # O(n)
        print(item)
    for a in items:          # O(n²) nested loop
        for b in items:
            print(a, b)
# Total: O(n) + O(n²) = O(n²) — the dominant term wins

When two terms are added, keep the one that grows faster. O(n² + n) simplifies to O(n²), because for large n the quadratic part dominates.

🏷️ The Common Complexity Classes

What each one looks like in real code

⚡

O(1) — Constant

Best

Cost is independent of input size. Dictionary lookups, arithmetic, and indexing by position are all O(1).

def first_item(items):
    return items[0]        # O(1) — indexing a list is constant

def lookup(mapping, key):
    return mapping[key]        # O(1) — dict lookup

def add(a, b):
    return a + b               # O(1) — arithmetic
🔍

O(log n) — Logarithmic

Excellent

Each step halves the remaining work. Binary search is the classic example. A 1,000,000-item search takes about 20 steps.

def binary_search(sorted_items, target):
    lo, hi = 0, len(sorted_items) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if sorted_items[mid] == target:
            return mid
        elif sorted_items[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
# Each iteration halves the search space: O(log n)
📏

O(n) — Linear

Good

Cost scales directly with input size. A single pass over a collection. Doubling the input doubles the time.

def find_max(items):
    best = items[0]
    for item in items:        # one pass
        if item > best:
            best = item
    return best

def sum_all(items):
    total = 0
    for item in items:        # one pass
        total += item
    return total
🔀

O(n log n) — Linearithmic

Fair

A linear pass that also does logarithmic work per item. This is the complexity of efficient sorting algorithms like merge sort and Python's sorted().

def merge_sort(items):
    if len(items) <= 1:
        return items
    mid = len(items) // 2
    left = merge_sort(items[:mid])
    right = merge_sort(items[mid:])
    return merge(left, right)

# log n levels of recursion × O(n) merge per level = O(n log n)
🔁

O(n²) — Quadratic

Slow

Nested loops over the same collection. For 10,000 items, that's 100 million operations. Often avoidable with a set or dict.

def find_duplicates_slow(items):
    duplicates = []
    for i in range(len(items)):          # O(n)
        for j in range(i + 1, len(items)):  # O(n) inner
            if items[i] == items[j]:
                duplicates.append(items[i])
    return duplicates
# O(n²) — for 10k items, ~50M comparisons
💥

O(2ⁿ) — Exponential

Very Slow

Each additional input doubles the work. Naive recursive Fibonacci is the textbook example. Only viable for very small inputs.

def fib_naive(n):
    if n < 2:
        return n
    return fib_naive(n - 1) + fib_naive(n - 2)
# O(2ⁿ) — fib(40) takes about 2 billion calls
The rule of thumb for sorting: O(n log n) is the best you can do with comparison-based sorting. Python's sorted() and .sort() use Timsort, which is O(n log n) in the worst case and O(n) on already-sorted data.

💾 Space Complexity

Memory grows too — measure it the same way

Space complexity describes how memory usage grows with input size. It uses the same notation as time complexity: O(1) means constant extra memory, O(n) means memory proportional to input size, and so on.

space_complexity.py 
# O(1) space — uses a fixed number of variables
def sum_in_place(items):
    total = 0
    for item in items:
        total += item
    return total

# O(n) space — allocates a new list proportional to input
def double_all(items):
    result = []
    for item in items:
        result.append(item * 2)
    return result

# O(n) space — a set can grow to the size of the input
def unique_items(items):
    return list(set(items))

Trading space for time

A common optimization is to spend more memory to save time. The find_duplicates example from the hero is exactly this: a set uses O(n) extra memory, but turns an O(n²) nested loop into an O(n) single pass.

def find_duplicates_slow(items):
    duplicates = []
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j]:
                duplicates.append(items[i])
    return duplicates
# Time: O(n²) · Space: O(1) extra

def find_duplicates_fast(items):
    seen = set()
    duplicates = []
    for item in items:
        if item in seen:
            duplicates.append(item)
        seen.add(item)
    return duplicates
# Time: O(n) · Space: O(n) extra
The classic trade-off: almost every speed optimization costs memory. Big-O lets you reason about the trade explicitly instead of discovering it when the process gets OOM-killed in production.
Recursion uses stack space. A recursive function that recurses n levels deep uses O(n) space even if it allocates no other structures. Python's default recursion limit is about 1,000 frames.

Building a string with += in a loop is O(n²), because each concatenation copies the existing string. Use "".join(parts) instead — it's O(n).

🔬 Deriving Complexity From Code

A step-by-step method

The method is simple: count the loops, look at what happens inside them, and combine the pieces. Most real code falls into a handful of patterns once you start looking.

analysis_examples.py 
# 1. Single loop over the input: O(n)
def count_positive(items):
    count = 0
    for item in items:
        if item > 0:
            count += 1
    return count

# 2. Two sequential loops: O(n) + O(n) = O(n)
def count_and_sum(items):
    count = 0
    for item in items:
        count += 1
    total = 0
    for item in items:
        total += item
    return count, total

# 3. Nested loops over the same input: O(n²)
def pairs(items):
    result = []
    for a in items:
        for b in items:
            result.append((a, b))
    return result

# 4. Loop that halves: O(log n)
def count_doublings(n):
    steps = 0
    while n > 1:
        n = n // 2
        steps += 1
    return steps

# 5. Loop with a set inside: O(n)
def has_duplicates(items):
    seen = set()
    for item in items:        # O(n)
        if item in seen:      # O(1)
            return True
        seen.add(item)
    return False

# 6. Loop with a list search inside: O(n²)
def has_duplicates_slow(items):
    seen = []
    for item in items:        # O(n)
        if item in seen:      # O(n)
            return True
        seen.append(item)
    return False

The three questions

  • How many times does each loop run?
  • What is the cost of the operations inside the loop?
  • Do the loops nest, or run sequentially?

Nested loops multiply. Sequential loops add. A loop that halves the problem each iteration is logarithmic. A loop with an O(1) operation inside is O(n); a loop with an O(n) operation inside is O(n²).

Hidden complexity in Python

What looks cheapActuallyWhy
x in some_listO(n)Linear scan
list.insert(0, x)O(n)Shifts every element
s += char in a loopO(n²)Each concatenation copies
some_list[1:]O(n)Creates a new list
list.pop(0)O(n)Shifts every element
sorted(x) inside a loopO(n² log n)Sorts on every iteration
The most expensive line in Python is often the one that looks cheapest. x in items reads like a single operation but is a full scan on a list. Switching to a set is a one-line fix that turns O(n²) into O(n).

Optimizing with the right structure

# Before: O(n × m) — for each item in a, scan all of b
def common_slow(a, b):
    result = []
    for item in a:
        if item in b:        # O(m) scan of list b
            result.append(item)
    return result

# After: O(n + m) — build a set once, then O(1) lookups
def common_fast(a, b):
    b_set = set(b)              # O(m) one-time cost
    return [item for item in a if item in b_set]
    # O(n) total

# Even simpler: set intersection is O(min(len(a), len(b)))
def common_fastest(a, b):
    return list(set(a) & set(b))

This is the pattern behind most real-world Python performance fixes: replace a list membership test with a set membership test, or replace a nested loop with a dictionary lookup.

🏗️ Mini Project — Three Ways to Find Duplicates

Measure the difference Big-O predicts

This program implements three versions of "find duplicates" with different complexity classes, then measures them at increasing input sizes so you can see the curves diverge.

duplicates_benchmark.py 
import time
import random

def dupes_quadratic(items):
    seen = []
    dupes = []
    for item in items:        # O(n)
        if item in seen:      # O(n) list scan
            dupes.append(item)
        else:
            seen.append(item)
    return dupes
# Time: O(n²)

def dupes_linear(items):
    seen = set()
    dupes = []
    for item in items:        # O(n)
        if item in seen:      # O(1) set lookup
            dupes.append(item)
        else:
            seen.add(item)
    return dupes
# Time: O(n)

def dupes_counter(items):
    from collections import Counter
    counts = Counter(items)    # O(n)
    return [item for item, count in counts.items() if count > 1]
# Time: O(n)

def benchmark(fn, n):
    data = [random.randint(0, n // 2) for _ in range(n)]
    start = time.perf_counter()
    fn(data)
    return time.perf_counter() - start

sizes = [500, 1000, 2000, 4000]

print(f"{'n':>8} {'quadratic':>12} {'linear':>12} {'counter':>12}")
for n in sizes:
    t_q = benchmark(dupes_quadratic, n)
    t_l = benchmark(dupes_linear, n)
    t_c = benchmark(dupes_counter, n)
    print(f"{n:>8} {t_q:>11.4f}s {t_l:>11.4f}s {t_c:>11.4f}s")

The output will show the quadratic version growing roughly 4x each time the input doubles, while the linear versions grow roughly 2x. That's the O(n²) versus O(n) signature in raw numbers — and it's exactly what the theory predicted.

The point of the exercise: at n = 500 the three versions look comparable. At n = 4,000 the quadratic one is already noticeably slower. At n = 100,000 it becomes unusable. Big-O tells you this in advance so you don't ship the wrong version.

That subset prevents most performance bugs and requires almost no effort to learn. The full formalism is more useful for algorithm design than for writing application code.

Sets are implemented as hash tables. Checking membership computes the hash of the value and jumps directly to the corresponding bucket, which is a constant-time operation. Dict and set operations are O(1) on average but O(n) in the worst case, if every key collides into the same bucket. In practice Python's hash functions make this rare for typical data, but it's the reason the docs say "average" rather than just O(1). For strings specifically, hash randomization (enabled by default) prevents adversarial collision attacks.
