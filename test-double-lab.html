03 — The Idea

What Is Duck Typing, Really?

"If it walks like a duck and quacks like a duck, it is a duck." In Python, an object is judged by the methods it has, not by what it inherits from. Your app doesn't care that FakeFile is unrelated to RealFile — it cares that both respond to read() and write().

🔌 Real-world analogy: the USB port

A USB port doesn't know or care if you plug in a mouse, a keyboard, a hard drive or a fan. As long as the device speaks USB, it works. Your app is the port; every file backend is a device. Test doubles exist precisely because the port is so easy to plug things into — you can substitute a fake for the real thing and the app never notices.

The contract: a file backend must provide write(name, text) and read(name). That's it. No base class, no typing.Protocol required — though both are useful when you want the promise written down.

The four kinds of test double

🎭

Stub

Returns canned data, ignores input. Fast, deterministic, no side effects.

class Stub: def read(...): return "..."
🕵️

Spy

Like a stub, but records every call so you can assert on it after.

self.calls = []
🧪

Fake

A working implementation with a shortcut — an in-memory database, a dict instead of a file.

self.store = {}
⚠️

Mock

A stub with expectations baked in — fails if not called correctly.

assert called_once_with(...)

All four work the same way from the app's point of view: they expose the methods the app calls. Which one you reach for depends on what you want to test.

Why bother? Three payoffs

  • Fast tests. An in-memory fake runs in microseconds. Disk, network and database calls take milliseconds to seconds.
  • Deterministic tests. A stub always returns the same thing. A real disk can be full, a network can be down, a clock can roll over.
  • Testable error paths. Hard to make a real disk fail on demand; trivial to make FlakyFile raise.

The rule that keeps this honest: a test double must respect the real object's contract. If RealFile.read raises FileNotFoundError for a missing file, FakeFile must too — otherwise your tests pass while production breaks.

🕰️ A short history of the idea

The phrase “duck test” (if it walks and quacks like a duck, it is a duck) is old and often attributed to the poet James Whitcomb Riley. Programmers borrowed it for a very practical question: how do you decide whether an object is usable? Two answers compete.

  • Nominal typing — an object is usable if it declares membership: it inherits from the right class, or is registered with it. Java and C# work this way, and in Python so do abstract base classes (abc, introduced by PEP 3119).
  • Structural typing — an object is usable if it has the right shape: the methods and attributes the caller needs. Plain Python behaves this way at runtime, and typing.Protocol (PEP 544, Python 3.8) brings the same idea to static type checkers.

The official Python glossary defines duck-typing as exactly this: judge an object by its methods and attributes rather than its type, and avoid tests such as isinstance() where possible. The test-double vocabulary comes from a different tradition: Gerard Meszaros introduced the term test double in his book xUnit Test Patterns (2007), borrowing from the stunt double in films.

🧪 The full family of test doubles

Earlier we met four kinds. Meszaros’s catalogue has five; the fifth, the dummy, is the simplest of all. Use this table as a field guide.

DoubleHas real behaviour?Records calls?Fails the test itself?Use it when…
DummyNoNoNoA parameter must be filled but is never used, e.g. greet(None, ...) in a branch that never touches the backend.
StubCanned answers onlyNoNoYou need one specific answer: “pretend the file contains X”.
SpyOptionalYesNo (you assert afterwards)You must prove the app did something: sent, wrote, retried.
FakeYes, simplifiedOptionalNoThe app needs a working substitute: dict instead of disk, SQLite in memory.
MockScriptedYesYes (expectations built in)The interaction itself is the requirement, and you want the test to fail loudly if it differs.

Everyday speech often says “mock” for all five. That is common, but knowing the differences helps you choose the cheapest double that proves what you need.

⚖️ Two styles of checking: state vs behaviour

Martin Fowler’s essay Mocks Aren’t Stubs describes two schools of test. State verification runs the code and then inspects results: “the greeting returned was Hello, Ana!”. Behaviour verification checks the conversation: “write was called once, then read”. Neither is better in general.

  • Prefer state checks when the result is observable — they survive refactoring because they ignore how the code works.
  • Prefer behaviour checks when the side effect is the product: an email sent, a payment requested, a retry attempted.
  • Fakes lean towards state checks; spies and mocks lean towards behaviour checks.

🏛️ Three principles hiding underneath

  • Dependency injection. Code that receives its collaborators can be given a different one. greet(backend, name) is the smallest example imaginable.
  • Behavioural substitutability (the Liskov idea). A double can stand in for the real object only if it keeps the same promises: same method names, same parameters, same return types, same exceptions in the same situations. This is the formal version of “mirror the contract”. Duck typing gives you no inheritance to enforce it, so tests must.
  • Seams. Michael Feathers calls a place where you can change behaviour without editing the code a seam. The backend parameter is a seam: the app’s source never changes, only what is plugged into it.

Why this matters beyond tests: the same seam lets you add logging, retries, caching, encryption or a cloud backend later, without touching the app. Testing is just the first customer.

🔍 Code-reading guide

  • FakeFile — a dict, plus the two methods. That's a fake.
  • FlakyFile(FakeFile) — inherits the methods, overrides write to randomly raise. super().write() delegates the successful branch to the parent.
  • SlowFile — same idea, but tracks a call counter. Real-world SlowFile would time.sleep(1) — the point is that in the test we can skip the wait entirely.
  • RealFile — no parent at all. Yet the same greet() accepts it, because it exposes the same two methods.
  • greet() — the app. Not a single isinstance, not a single hasattr. It just calls the methods and trusts the caller to pass a conforming object.
  • The final loop — hasattr verifies that all four backends satisfy the contract, without any of them sharing a base class.
06 — Inside the Dispatch

How Duck Typing Works Under the Hood

Attribute lookup in one table

When your app calls backend.write("x", "y"), Python performs two lookups — one for write on the object, one for the result of calling it with those arguments. Here is what it finds per backend:

ObjectResolves toBehaviour
FakeFileFakeFile.writeStores text in a dict.
FlakyFileFlakyFile.writeMaybe raises IOError, else delegates to FakeFile.write.
SlowFileFakeFile.write (inherited)Behaves like FakeFile for writes; overrides read only.
RealFileRealFile.writeWrites to the filesystem.
A random object()not foundRaises AttributeError: 'object' object has no attribute 'write'

Notice that SlowFile inherits write from FakeFile — that's method lookup going up the MRO. But RealFile has no parent, so its write must come from the class itself. Both are found the same way: an attribute lookup on the instance.

Protocol: writing the contract down

Duck typing is great at runtime, but it fails late — if the caller passes the wrong object, the error appears on the first method call inside the app. typing.Protocol catches that earlier, at type-check time, without forcing inheritance.

You already use this daily. print(x, file=f) works with any object that has .write() — a real file, io.StringIO, or your own class. That's duck typing in the standard library.

EAFP vs LBYL

Two styles of handling "it might not work":

StyleMeaningExample
LBYLLook Before You Leap — check firstif name in backend.store: backend.read(name)
EAFPEasier to Ask Forgiveness than Permission — try it, catch the errortry: backend.read(name) except FileNotFoundError: ...

Duck typing leans EAFP. You don't check that write exists — you call it and catch AttributeError at the outer boundary if you must. But wrap small blocks, not whole functions: a broad except AttributeError will also hide typos inside the method body.

Mocking with unittest.mock

Python ships a built-in Mock class that auto-generates methods. It is the fastest way to get a stub, but it has no idea what the real object does — so use it when you want a spy, and use a hand-written class when you want realistic behavior.

Side-by-side: strict typing vs duck typing

The table above is a summary. This program lets you observe the same facts: the class search order, inherited versus overridden methods, bound methods, and the exact error a wrong guess produces.

Key insight: methods live in classes, data lives in the object’s __dict__, and a lookup walks the chain from the object to its class to the parents. Duck typing works because this search happens at the moment of the call, using only the name.

When duck typing is the wrong tool: when a wrong object would fail silently or far from the cause (for instance data gets written and corrupted before the failing call), or when many teams depend on the contract and need it enforced. Add a Protocol or a contract test (next section) — do not abandon duck typing, just write the promise down.

07 — Real-World Patterns

From Toy Examples to Professional Habits

The earlier sections taught the mechanism. This section shows the six habits that experienced Python developers build on top of it. Each has a runnable program with a full line-by-line explanation.

1 · Three ways to inject a backend

Passing the dependency as a function parameter is only one option. Classes usually take it in the constructor, and long-lived objects often accept an optional one with a sensible default.

TechniqueUse whenTrade-off
ParameterA single function needs itYou pass it on every call.
ConstructorSeveral methods share itThe object is tied to one backend for its life.
Default argumentProduction should work with zero setupThe default can hide a real dependency, so test code must remember to override it.

2 · Injecting time: making slow things fast

Waiting is a dependency like any other. If the delay is a parameter, the test can replace “wait two seconds” with “write the number down”. The same trick works for clocks (now=datetime.now) and random numbers.

Duck typing is not only for objects. The “sleep” here is anything callable with one number: time.sleep, a lambda, or list.append.

3 · Composing backends like Lego

Since every backend promises the same two methods, a backend can hold another backend and add behaviour around it: logging, retrying, caching, encryption, metrics. The app still sees one object. This is the Decorator (or wrapper) pattern, and duck typing makes it almost effortless.

4 · A real test with unittest

Python ships with a test framework. This program defines three tests: the happy path, a state change and an error path, all against fakes, and runs them in the browser.

Rule of thumb for good tests: one behaviour per test, a name that reads like a sentence, a fresh double for every test, and no test that depends on another.

5 · The same test with pytest

Most professional projects use pytest. Its fixtures and plain assert statements remove boilerplate, and a parametrised fixture can run every test against several backends.

6 · Contract tests: stop fakes from lying

The biggest risk of any test double is that it drifts away from the real thing. A contract test is a single checklist run against every implementation. If the real file passes and the fake fails, the fake is wrong — and you find out in a second, not in production.

Make it a habit: whenever you write a new double, add its class to the contract test’s list. One extra line protects every test that uses it.

🧭 Which double should I write?

  1. Does the code under test ignore this dependency? Pass a dummy (None or object()).
  2. Do I need only one canned answer? Write a stub, or Mock(return_value=...).
  3. Do I need a working substitute? Write a fake and put it under a contract test.
  4. Must I prove a call happened? Add recording (spy) or use Mock.assert_called_once_with.
  5. Do I need to cause failures or delays on demand? Write a tiny special-purpose double or a wrapper like RetryBackend.

When two answers fit, choose the simplest one. A stub that is five lines long is easier to trust than a fake that is fifty.

08 — Break It On Purpose

Four Classic Test-Double Mistakes

The fastest way to understand the rules is to watch them fail. Run each broken example, read the error, then run the fix.

Mistake 1 — A fake that lies about the real contract

The real backend raises on a missing file. The fake returns an empty string — so the app "works" in tests but crashes in production.

✓ Fix: mirror the real contract

Mistake 2 — Wrapping too much in except AttributeError

A broad exception handler hides both "the object has no method" and "the method has a typo inside it".

✓ Fix: catch only what you intend

Mistake 3 — Testing the double instead of the app

If the test asserts on how the fake stored its data, you're testing the fake, not the behaviour. Change the fake's internals — the test should still pass.

✓ Fix: assert on what the app should return

Mistake 4 — Forgetting to clean up after a real backend

Real file tests that don't clean up leave debris. Your next run may behave differently because the file already exists.

✓ Fix: tmp_path, try/finally, or a fake

🩺 Error-message decoder

Duck typing shows its mistakes as ordinary Python exceptions. Learn to read the message and you can usually fix the problem in seconds.

Debug habit: when a test fails, first check whether the double matches the real object's contract. Nine times out of ten, the fake lies.

11 — Review

Key Takeaways

  • Duck typing judges an object by its methods, not its class ancestry.
  • Test doubles (stubs, spies, fakes, mocks) plug into the same slot as the real object if they honor the contract.
  • Pass the backend in — one small change to the app buys infinite testability.
  • Mirror the contract: if the real backend raises, the fake must raise too.
  • Use Protocol when you want the contract written down and checked by a type checker.
  • Wrap small blocks in try/except — a broad except AttributeError hides real bugs.
  • Inject everything slow or random — backends, clocks, sleeps — so tests control them.
  • Run a contract test over the real object and every fake so doubles cannot drift.
  • Choose the simplest double that proves what you need: dummy, stub, spy, fake, then mock.

Frequently Asked Questions

Is duck typing the same as polymorphism?

Not quite. Polymorphism is the idea of "one interface, many implementations." Duck typing is one way to achieve it in Python — the version that doesn't need a shared parent class. Method overriding via inheritance is another way.

When should I use unittest.mock.Mock vs a hand-written fake?

Use Mock when you just need a spy — a quick placeholder that records calls. Use a hand-written fake when you need realistic behavior (a working dict-backed file, an in-memory database). Hand-written fakes respect the real contract; mocks won't stop you from writing a fake that lies.

Does duck typing make bugs harder to find?

It can — a wrong object surfaces its error on the first method call, not at the declaration. Two mitigations: (1) add a typing.Protocol so the type checker catches it; (2) keep the boundary small — pass one backend in, don't forward it through ten layers.

Why is FakeFile an acceptable test double but Mock() can also be one?

Because the app only checks for methods — that's duck typing. Anything with write() and read() is accepted, whether it's a real class, a fake, a spy or a Mock. The choice is about what you want to verify, not whether the app will accept it.

What if my test needs to check write() was called with specific arguments?

That's what a spy is for. Use Spy from challenge 1 or unittest.mock.Mock: mock.write.assert_called_once_with("greeting.txt", "Hello, Ana!"). But resist the urge to assert on internals — most tests should assert on what the app returned, not on how many times a private method was called.

Why does my fake need super().__init__()?

When a subclass defines its own __init__, Python no longer runs the parent’s automatically. If the parent’s initialiser creates self.store and you skip it, the first write fails with AttributeError: ... no attribute 'store'. Call super().__init__() as the first line of your own initialiser.

Is it wrong to use isinstance in Python?

No — it is sometimes the right tool, for example when the code genuinely behaves differently for strings and lists. The guideline is narrower: do not use isinstance to gatekeep dependencies that only need a couple of methods, because that blocks perfectly good substitutes such as test doubles.

Should I test my fakes?

Yes, but cheaply: one contract test that runs against the real implementation and every fake. If a fake and the real thing ever disagree, the contract test shows it immediately. You do not need separate unit tests for each method of each fake.

How is a fake different from a mock in practice?

A fake works: write then read returns your text, like a small real file. A mock only scripts answers and checks calls. With a fake, assertions look at results; with a mock they look at calls. If the app logic depends on remembered data, a fake is usually less brittle.

Can I use a dictionary directly as a backend?

Only if the app calls dictionary-style operations. greet calls .write() and .read(), which dictionaries do not have, so a plain dict fails with AttributeError (the lab’s “Break the contract” button shows exactly that). You would write a small adapter class around the dictionary.
