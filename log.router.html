01 — The Idea

Why a "Log Router"?

📨 One Function, Four Formats

Logging systems receive wildly different things: a plain message, structured JSON, an exception object, a blob of bytes. The naive fix is a chain of isinstance checks inside one giant function. The polymorphic fix is @singledispatch: one function name, one signature, and a separate implementation registered per type.

The call site — emit(message) — never changes. Add a new type tomorrow, and the call site still doesn't change. That is open/closed in a single decorator.

Runnable in-browser code Interactive type router Line-by-line walkthrough Cheat sheet & quiz Pyodide playground

Why @singledispatch rather than a class hierarchy?

You cannot edit str, dict, Exception or bytes to add an emit() method — they are built-ins. Single dispatch lets you register behavior externally, keyed on the type, without touching the classes.

The alternative would be subclassing str and dict just to attach a method — heavy and surprising. Dispatch by type keeps the built-ins alone and puts the routing in one function.

🤔 What does “dispatch” mean?

Dispatching means choosing which piece of code to run for a call. In everyday object-oriented code Python dispatches on the object a method belongs to: dog.speak() and cat.speak() run different code because dog and cat have different classes. Single dispatch uses the same idea, but for an ordinary function and keyed on the type of its first argument. The function is outside the classes, so it works even for classes you did not write.

🏷️

Methods on your class

Best when you own the class: shape.area(). The behaviour lives inside the type.

🦆

Duck typing

Best when objects already share a method name. No registry, no type checks; see the Test Double Lab.

🚦

Single dispatch

Best when the types are not yours (str, dict, third-party classes) and you want one function name for all of them.

🪜 The problem, shown: the isinstance ladder

Here is the router written without @singledispatch. It works, and it is the version most programmers write first. Read it line by line, and pay special attention to the last six lines: they reveal a bug that has nothing to do with typos.

Why the ladder hurts: (1) every new type means editing this one function; (2) the order of the checks silently changes the result, as emit_wrong_order(True) proved; (3) a plugin in another file cannot add a rung without touching your source; (4) the whole function must be tested as one unit. The rest of this lesson shows how @singledispatch removes all four problems.

02 — Python Primer

Two Python Ideas Behind Every Line

The router rests on two ideas that beginners often meet here for the first time: types and their family trees (the MRO) and decorators. If you already know both, skim the cards and jump to the live router. If not, each idea has a short program you can run and read line by line.

How to study with this page. ① Predict: open “Predict first” and guess the output before pressing Run. ② Run the program. ③ Read the line-by-line explanation: tap any line, or switch on Step mode and press Next to go one line at a time while the matching line lights up. ④ Change one thing in the playground and predict again.

🌳 Idea 1 — every value has a type, and types form a family tree

When Python creates 42 it creates an object of class int. Classes can inherit from other classes, and the ordered list of ancestors is called the MRO (Method Resolution Order). @singledispatch uses nothing except this list: it takes the type of your argument, walks its MRO from the front, and runs the first handler it has registered.

bool→int→object
ValueError→Exception→BaseException→object

Takeaway: type(x) is the exact class, isinstance(x, C) is “C or any of its subclasses”, and __mro__ is the search path. Remember that bool is a kind of int.

🎀 Idea 2 — a decorator is a function that receives a function

You will see @singledispatch and @emit.register above function definitions. The @ line is just a shortcut for name = decorator(name). Two flavours matter here: a decorator that wraps a function in a new one, and a decorator that records a function and returns it unchanged. @emit.register is the second kind.

Takeaway: @emit.register does not change your handler; it stores it in a table when the file is loaded. That table is what the dispatcher searches at call time.

🗒️ Three small reminders used on this page

F-STRINGS

f"{x!r}"

Inserts x into the text. !r uses repr(), so strings keep their quotes and the output is unambiguous.

ANNOTATIONS

message: str

A label saying what type a parameter is meant to be. Python ignores it at run time, except that @emit.register reads it.

NAMING

def _(...)

A single underscore is the conventional name for “I will never call this directly”. Handlers are reached through emit.

04 — Under the Hood

How @singledispatch Works

When you call emit(x), Python does not run the function body directly. The dispatcher inspects type(x), looks for a registered handler, and calls it. Three programs below take the mechanism apart: first a hand-built version, then the real registry, then the famous bool surprise.

The dispatch algorithm

  1. Take the type of the first positional argument. cls = type(args[0]). Keyword arguments are not used: emit(message="hi") raises TypeError: emit requires at least 1 positional argument.
  2. Check the cache. If this class was looked up before, reuse the answer.
  3. Walk the class’s MRO from the most specific class to object. If abstract base classes (such as Mapping) are registered, the dispatcher slots them into the right place in that search order.
  4. The first registered class wins. If two unrelated ABCs match equally well, Python raises RuntimeError: Ambiguous dispatch instead of guessing.
  5. Fallback. The base function is registered for object, so a match always exists.
  6. Cache and invalidate. The result is cached; every call to register clears the cache.

⚖️ The bool / int surprise

Rule: registering int also captures bool, until you register bool yourself. Registration order does not matter; the position in the MRO does.

Design notes

08 — Where It Fits

Patterns This Enables

Single dispatch is a small tool with outsized impact. These are the patterns you can build with it.

🔌

Plugin Systems

Each plugin registers a handler for its own event type. Core dispatch code never imports plugins directly.

📦

Serialization

One serialize(obj) that handles dict, list, datetime, UUID, your domain models — without if/elif.

📊

Report Rendering

Render any result type as a chart or table: register a handler per metric type, one render(result) call site.

🧪

Test Data Builders

Each domain type has a handler that returns realistic sample data. Build fixtures by type, not by hand.

🎨

Type-Routed APIs

Framework routes incoming request.data to the right handler based on its type — JSON, form data, file upload, raw bytes.

📣

Notification Delivery

One notify(message) route — Email, SMS, Push payloads each handled by their registered function.

17 — Wrapping Up

Takeaways

🏁 What You've Learned

You saw how a single emit(message) call routes plain strings, structured JSON, exception objects and raw bytes to four different handlers — with no isinstance ladder anywhere. That is single-dispatch polymorphism.

You also saw why this is open/closed: extending the router is a new @emit.register function, never a modification of the call site. And you confirmed the sharp edges — bool is an int, annotations are required, only the first argument dispatches.

Live router + code Line-by-line walkthrough Extending & pitfalls Cheat sheet & quiz

Key Takeaways

  • @singledispatch turns one function name into a dispatcher — handlers are registered by type.
  • Dispatch walks up the MRO: closest registered ancestor wins, base function is the fallback.
  • Only the first argument dispatches — for two-dimensional routing, use a dict keyed by (type1, type2).
  • bool is a subclass of int — register bool explicitly if you want it treated separately.
  • Registration order never matters; MRO position does. An explicit bool handler beats int in any order.
  • Extend without modifying — the call site never changes, so existing tests stay green.
  • Best for unowned types — built-ins, third-party classes, or domain types you shouldn't subclass.

🙋 Frequently asked questions

When should I NOT use @singledispatch?

When you own the classes, give them a method (obj.emit()). When two or three types are involved and will never grow, a plain if isinstance is simpler. Dispatch pays off when types are open-ended.

Why does my second parameter's annotation do nothing?

Only the first positional argument is used. See the mistakes section; use a table keyed by type pairs.

Is it slow?

Lookups are cached per class, so repeated calls are cheap. Registering clears the cache.

Can I dispatch on a method's argument?

Yes: functools.singledispatchmethod, shown in section 06.

📚 Glossary

Dispatch

Choosing which code runs for a call.

Handler

A function registered for one type.

Registry

The type-to-function table.

MRO

Ordered list of a class and its ancestors.

Decorator

A function that takes a function.

ABC

Abstract base class such as Mapping.

Fallback

The base function, registered for object.

Open/closed

Extend by adding code, not editing.
