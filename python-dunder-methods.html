Python Dunder Methods
Teach your objects to speak Python

Dunder (double-underscore) methods, also called magic methods, are the hooks that let your own classes work with print(), len(), +, ==, for loops, with blocks, and more. This lesson explains the idea from scratch and walks through 15 runnable programs, each one explained line by line.

📖 Welcome: Why Dunder Methods Matter

🤔 The big idea

Try this in any Python shell: len("hello"), [1, 2] + [3], "a" < "b", for x in range(3). These all feel like language features. They are not magic. Each one is Python quietly calling a specially named method on the object you gave it.

When you write len(x), Python calls x.__len__(). When you write a + b, Python calls a.__add__(b). When you write print(x), Python calls x.__str__(). The names start and end with two underscores, which is where the nickname "dunder" ("double under") comes from.

This means the built-in types (int, str, list, dict) have no special powers. They simply implement these methods. If your class implements the same methods, your objects become first-class citizens that behave exactly like the built-ins.

💡 Python's official name for this system is the Python Data Model. Learning it is what separates "I can write classes" from "I write classes that feel like part of the language."

🎯 What you will learn

  • ✓What a dunder method is, who calls it, and why you almost never call it yourself
  • ✓How objects are created: __new__ and __init__
  • ✓How to control printing and debugging output with __repr__, __str__, and __format__
  • ✓How to make objects comparable, sortable, and usable in sets and as dictionary keys
  • ✓How to overload operators such as +, *, unary -, abs(), and +=
  • ✓How to build custom containers (len(), indexing, in, del) and iterators
  • ✓How to make objects callable, usable in with blocks, and smart about attribute access
  • ✓How to avoid the classic mistakes (like defining __eq__ and breaking hashing)

⚙️ How Dunder Methods Actually Work

🔄 Syntax → method call

Python translates everyday syntax into method calls on the type of the object. This translation is called the protocol for that feature.

You writePython callsFeature
Book("Dune", 612)__new__, then __init__Creating objects
print(x) / str(x)x.__str__()Friendly text
repr(x) / REPL displayx.__repr__()Developer text
a == ba.__eq__(b)Equality
a + ba.__add__(b)Arithmetic
len(x)x.__len__()Size
x[i]x.__getitem__(i)Indexing
for i in xx.__iter__(), __next__()Iteration
f(3)f.__call__(3)Callable objects
with x as y__enter__, __exit__Context managers

📜 Five golden rules

  • 1Let Python call them. Write len(x), not x.__len__(). The built-in adds checks and sometimes a faster path.
  • 2Never invent your own dunder names. Names like __total__ are reserved for Python's future use. Use a single underscore for your own helpers.
  • 3Return what the protocol expects. __len__ must return a non-negative int, __str__ must return a str, and so on.
  • 4Return NotImplemented (not raise) when you don't know how to handle the other operand. This lets Python try the other object's method.
  • 5Implement only what you need. A class with a few well-chosen dunders is better than one that implements everything.
💡 Python looks dunder methods up on the class, not on the individual instance. Assigning obj.__len__ = lambda: 5 will not make len(obj) work.

🦆 Connection to duck typing and polymorphism

Python does not ask "are you a list?" It asks "can you do what a list does?" If your class has __len__ and __getitem__, it behaves like a sequence. Python code that works with sequences will happily accept it. This is the practical heart of polymorphism in Python.

Lesson 2

🏗️ Creating Objects: __new__ and __init__ Intermediate

Most developers know __init__, but creating an object is really a two-step process:

  1. __new__(cls, ...) builds a blank object and returns it. It is a static-style method that receives the class.
  2. __init__(self, ...) fills in that object. It receives the finished blank object as self and must return None.

You will write __init__ constantly and __new__ rarely (immutable types, singletons, and some frameworks). Seeing the order once makes the whole object model click.

Lesson 3

🖨️ Representing Objects: __repr__, __str__, __format__ Beginner

Without these, printing your object gives something like <__main__.Temperature object at 0x7f...>, which helps nobody. Python has two text forms:

  • __repr__ is for developers. It should be unambiguous, ideally looking like the code that would recreate the object. It is used in the REPL, in debuggers, and when objects sit inside lists.
  • __str__ is for users. It should be readable and friendly. It is used by print(), str(), and f-strings.

If you define only one, define __repr__. When __str__ is missing, Python falls back to __repr__.

Lesson 4

⚖️ Comparison and Hashing: __eq__, __lt__, __hash__ Intermediate

By default, two objects are equal only if they are the same object. Implementing __eq__ lets you say "equal means same contents." Implementing __lt__ (less than) lets you use sorted(), min(), and max().

Two helpers keep the code short:

  • functools.total_ordering generates <=, >, and >= for you if you provide __eq__ and one ordering method.
  • Comparing tuples compares item by item, which is a neat way to implement multi-field comparison.

__hash__ is the partner of __eq__: objects that are equal must have the same hash, otherwise sets and dictionaries break.

📦 Building Containers: __len__, __getitem__ and Friends Intermediate

To make a class feel like a list or dictionary, implement the container protocol:

  • __len__ powers len(x)
  • __getitem__ powers x[key] (reading)
  • __setitem__ powers x[key] = value
  • __delitem__ powers del x[key]
  • __contains__ powers item in x

Bonus: if a class has __getitem__ that accepts 0, 1, 2… and raises IndexError at the end, Python can already loop over it with for, with no extra code.

🔁 Making Objects Iterable: __iter__ and __next__ Intermediate

The iterator protocol has two parts:

  • __iter__() returns an iterator (an object that can hand out items one at a time).
  • __next__() returns the next item, or raises StopIteration when finished.

A for loop is just a while True that calls __next__ until StopIteration. An object can be its own iterator by returning self from __iter__. Such an iterator is single-use: once exhausted, it stays empty. For a deeper dive, see Iterators & Generators.

Lesson 9

🔐 Context Managers: __enter__ and __exit__ Intermediate

The with statement guarantees that cleanup code runs, even if an error occurs inside the block. Two dunders drive it:

  • __enter__(self) runs when the block begins. Its return value is what follows as.
  • __exit__(self, exc_type, exc_value, traceback) runs when the block ends, always. If an exception happened, its details are passed in; otherwise all three are None. Returning a true value tells Python to suppress the exception.

Lesson 10

🕵️ Controlling Attribute Access Advanced

You can intercept attribute access itself. The four hooks behave differently, and mixing them up is a classic source of bugs:

MethodWhen it runs
__getattribute__(self, name)Every attribute read (powerful and dangerous)
__getattr__(self, name)Only when the normal lookup fails (a fallback)
__setattr__(self, name, value)Every attribute assignment, including inside __init__
__delattr__(self, name)Every del obj.name

Prefer __getattr__ (a safe fallback) over __getattribute__. Inside __setattr__, do not write self.x = value, which would call __setattr__ again and recurse forever. Delegate to super().__setattr__ instead.

Lesson 11

✅ Truthiness: __bool__ and __len__ Beginner

Every if obj: or while obj: asks Python "is this object truthy?" Python decides in this order:

  1. If the class defines __bool__, use its result.
  2. Otherwise, if it defines __len__, the object is falsy when the length is 0.
  3. Otherwise, the object is always truthy.

This is why empty lists, strings, and dictionaries are falsy.

⚠️ Common Mistakes (and How to Avoid Them)

These two are responsible for a large share of dunder-related bugs.

❌ Mistake 1: defining __eq__ without __hash__

When you define __eq__ in a class, Python automatically sets __hash__ to None, making instances unhashable. They can then no longer go in sets or be dictionary keys.

⚠️ Only hash on fields that never change after creation. If an object's hash changes while it is inside a set or dict, lookups will silently fail.

❌ Mistake 2: raising errors instead of returning NotImplemented

If __eq__ meets a type it cannot handle, return NotImplemented. Python then tries the reflected operation on the other object and finally falls back to a sensible default, rather than crashing with AttributeError.

🚫 More pitfalls to watch for

  • ✗Calling dunders directly (x.__len__()) instead of the built-in (len(x)).
  • ✗Printing inside __repr__ or __str__ instead of returning a string. This returns None and raises TypeError.
  • ✗Forgetting return self in __iadd__ and similar in-place methods.
  • ✗Mutating operands in __add__. Return a new object instead.
  • ✗Recursion inside __setattr__ / __getattribute__. Use super() to reach the real storage.
  • ✗Inventing your own __something__ names. Use _something instead.
