Python Dunder Methods —
The Complete Guide to Magic Methods

Double-underscore methods like __init__, __str__, __eq__, and __len__ make your custom classes feel native to Python. This in-depth guide explains every method you'll actually use, when to reach for each one, common pitfalls to avoid, and best practices drawn from real-world Python codebases — all with runnable examples.

Introduction

What Are Dunder Methods and Why Do They Matter?

"Dunder" is shorthand for double underscore — methods with names like __init__ or __add__ that begin and end with two underscores. Python calls these methods automatically in response to specific syntax. When you write a + b, Python is really calling a.__add__(b). When you write len(x), it calls x.__len__(). When you write for item in collection, it calls collection.__iter__(). This is the mechanism that makes Python's built-in types and user-defined types work uniformly.

You almost never call dunder methods directly. Instead, you implement them on your classes so that built-in syntax — +, ==, <, in, for ... in, with, indexing with [] — works with your objects in a way that feels natural. This is what Python's documentation calls the data model, and it's one of the most important ideas to internalize if you want to write idiomatic Python.

The core idea: Dunder methods let you hook into Python's syntax. Implementing __len__ means len(your_obj) works. Implementing __getitem__ means you can index with your_obj[i]. Implementing __iter__ means you can use a for loop on it. You're not just adding methods — you're teaching Python how to treat your objects like first-class citizens.

Why Learn Dunder Methods?

Interoperability

Your custom classes work seamlessly with sorted(), len(), in, for loops, comprehensions, and the standard library — without writing adapters.

Expressiveness

Instead of v1.add(v2), users of your class can write v1 + v2. Instead of playlist.get_at(3), they can write playlist[3]. Syntax carries meaning.

Library Compatibility

Frameworks like NumPy, Pandas, PyTorch, and Django all rely on dunder methods. Understanding them makes you fluent in the wider Python ecosystem.

Deeper Understanding

Once you know dunders, you understand why Python behaves the way it does — why 2 == 2.0 is True, how with statements really work, and more.

Part 1

Most-Used Dunder Methods

These ten methods cover the majority of real-world use cases. Master these first and you'll rarely need anything else. If you're learning dunders for the first time, focus your study here.

Method Triggered by Purpose
__init__obj = Cls(...)Initialize a new instance
__str__str(obj), print(obj)Human-readable string
__repr__repr(obj)Developer-facing string (debuggable)
__eq__a == bEquality check
__lt__a < bLess-than comparison
__hash__hash(obj)Hash for use in dicts/sets
__len__len(obj)Length / size
__getitem__obj[i]Indexing / subscripting
__iter__for x in objIteration
__contains__x in objMembership test

Notice that none of these methods are called directly in normal Python code. You write len(x), not x.__len__(). You write for item in playlist, not playlist.__iter__(). This is intentional — the dunder methods exist to be discovered by Python's syntax, not to be invoked by you. Direct calls are considered bad style because they skip Python's type negotiation logic (which we'll cover in the arithmetic section).

Design principle: If your class logically is a collection, implement container methods. If it logically has a value, implement comparison and representation methods. If it logically does work, implement __call__ or context managers. Don't implement dunders that don't match the semantic reality of your class — a User class shouldn't have __add__ unless adding users is a meaningful operation.
Part 2

Representation: __str__ and __repr__

__repr__ should return a string that would recreate the object if evaluated — ideal for debugging. __str__ is for end users and is what print() uses. If __str__ is not defined, Python falls back to __repr__. This two-tier design is often misunderstood by beginners, so let's be precise about when each one matters.

Here's the rule of thumb professional Python developers follow:

  • __repr__ — aimed at developers. Should be unambiguous and, ideally, valid Python that recreates the object. Shown in the REPL, in lists, dicts, and logs.
  • __str__ — aimed at end users. Should be readable. Shown by print() and str().
python 
class Vector:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Vector({self.x!r}, {self.y!r})"

    def __str__(self):
        return f"({self.x}, {self.y})"


v = Vector(3, -4)
print(v)
print(repr(v))
print([v])
print(f"{v}")
Rule of thumb: Always define __repr__. Add __str__ only when you want a different (usually prettier) output for users. In notebooks, both look the same — but in interactive prompts, lists, and logs, __repr__ is what shows up. If your class has no __str__, print() falls back to __repr__, which is often fine.

The !r Format Specifier

You'll notice f"Vector({self.x!r}, {self.y!r})" — the !r tells the f-string to use repr() instead of str() on the value. This matters for strings: Vector('a', 1) with plain {self.x} would produce Vector(a, 1), which isn't valid Python. With !r, you get Vector('a', 1) — which is recreatable. This is the small detail that separates an adequate __repr__ from a great one.

Bonus: __format__

If you want your class to support f"{obj:spec}" with custom formatting, implement __format__(self, spec). You probably won't need this until you're writing a library — the default (delegating to str and ignoring the spec) is fine for most cases.

Part 3

Comparison and Hashing: __eq__, __lt__, __hash__

By default, == on custom objects compares identity — a is b. That's almost never what you want for a value-like class such as Money, Point, or DateRange. To make equality mean same value, define __eq__. Similarly, __lt__ enables < (and, via functools.total_ordering, unlocks the full set of comparisons), which also makes sorted() work on lists of your objects.

python 
from functools import total_ordering

@total_ordering
class Money:
    def __init__(self, amount, currency="USD"):
        self.amount = amount
        self.currency = currency

    def __repr__(self):
        return f"Money({self.amount}, {self.currency!r})"

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return self.amount == other.amount and self.currency == other.currency

    def __lt__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        if self.currency != other.currency:
            raise ValueError("Cannot compare different currencies")
        return self.amount < other.amount

    def __hash__(self):
        return hash((self.amount, self.currency))


prices = [Money(10), Money(3), Money(7)]
print(sorted(prices))
print(Money(5) == Money(5))
print(Money(5) == Money(5, "EUR"))
print(len({Money(5), Money(5), Money(3)}))
Return NotImplemented, not False, when you don't know how to compare against an unknown type. This tells Python to try the other object's reflected method, and finally fall back to identity comparison. Returning False short-circuits that negotiation — and can produce subtly wrong results when comparing against types you don't own.
Defining __eq__ sets __hash__ to None unless you also define __hash__. That's because mutable, value-comparable objects shouldn't be dict keys by default. To make your object hashable, add def __hash__(self): return hash((self.amount, self.currency)) — using the same fields your __eq__ compares. Otherwise, using your objects in a set or as a dict key raises TypeError: unhashable type.

Consistency Between __eq__ and __hash__

There's a strict contract you must uphold: if a == b is True, then hash(a) == hash(b) must also be True. Violating this contract silently breaks dicts and sets. If you define __eq__ based on certain attributes, you must hash exactly those attributes (or fewer — but never more, and never different ones). This is why the recommended pattern is to hash the same tuple your __eq__ compares.

The @total_ordering Shortcut

If you want all six comparison operators (<, <=, >, >=, ==, !=) to work, you don't need to implement all six. Define __eq__ and one other (typically __lt__), then decorate with @functools.total_ordering. Python generates the rest for you. This is cleaner and less error-prone than writing all six yourself.

Pitfall: Comparing with is by accident

Beginners sometimes implement __eq__ by returning self is other. That's the default behavior, so it adds nothing — and it likely masks the bug you were trying to fix. If a == b should mean "same values", you need to compare the attributes, not the object identities.

Part 4

Arithmetic Operator Overloading

Every operator has a dunder method. Implementing them lets your objects participate in natural expressions: v1 + v2, v * 3, -v. But before you overload +, ask: does adding two of these objects actually mean something? If it doesn't, don't implement it. Overloading operators on classes where they don't make semantic sense is a common source of unreadable code.

OperatorMethodExampleUse case
+__add__a + bVector addition, set union, string concat
-__sub__a - bVector subtraction, set difference
*__mul__a * bScalar multiplication, matrix product
/__truediv__a / bDivision (returns float)
//__floordiv__a // bFloor division (returns int)
%__mod__a % bModulo, clock arithmetic
**__pow__a ** bExponentiation
@__matmul__a @ bMatrix multiplication (NumPy)
unary -__neg__-aNegation
+=__iadd__a += bIn-place add (mutating)
python 
class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):
        return f"Vector({self.x}, {self.y})"

    def __add__(self, other):
        if isinstance(other, Vector):
            return Vector(self.x + other.x, self.y + other.y)
        return NotImplemented

    def __sub__(self, other):
        if isinstance(other, Vector):
            return Vector(self.x - other.x, self.y - other.y)
        return NotImplemented

    def __mul__(self, scalar):
        if isinstance(scalar, (int, float)):
            return Vector(self.x * scalar, self.y * scalar)
        return NotImplemented

    def __rmul__(self, scalar):
        return self.__mul__(scalar)

    def __neg__(self):
        return Vector(-self.x, -self.y)


a = Vector(2, 3)
b = Vector(4, -1)

print(a + b)
print(a - b)
print(a * 3)
print(3 * a)
print(-a)

Reflected and In-Place Operations

When you write 3 * a, Python first tries int.__mul__(3, a), which returns NotImplemented because int doesn't know about Vector. Python then falls back to a.__rmul__(3) — the "reflected" version. If you only implement __mul__ (for a * 3) but not __rmul__, then 3 * a raises TypeError. Implementing both is the safe choice when the operation is commutative.

In-place operators like += look for __iadd__ first, then fall back to __add__. If your class is immutable, you don't need to implement __iadd__ — the fallback creates a new object and rebinds the variable. If your class is mutable and you want += to mutate in place (like list does), implement __iadd__ explicitly.

Type negotiation in one sentence: For any binary operation, Python tries left.__op__(right), then right.__rop__(left), then raises TypeError. Returning NotImplemented from your method is how you participate in this dance correctly.
Part 5

Container Protocol

Make your class act like a collection. Implementing __len__, __getitem__, __contains__, and __iter__ gives you length, indexing, membership, and iteration — all with Python-native syntax. This is one of the highest-leverage places to use dunders because it makes your class instantly usable in comprehensions, for loops, and standard library functions like sum() and min().

python 
class Playlist:
    def __init__(self, songs=None):
        self._songs = list(songs or [])

    def __len__(self):
        return len(self._songs)

    def __getitem__(self, index):
        return self._songs[index]

    def __setitem__(self, index, value):
        self._songs[index] = value

    def __contains__(self, item):
        return item in self._songs

    def __iter__(self):
        return iter(self._songs)

    def __reversed__(self):
        return reversed(self._songs)

    def __repr__(self):
        return f"Playlist({self._songs!r})"


pl = Playlist(["Blue", "Idioteque", "Nude"])

print(len(pl))
print(pl[0])
print(pl[-1])
print(pl[0:2])
print("Nude" in pl)
print("Karma Police" in pl)

pl[0] = "Everything In Its Right Place"
print(pl[0])

for song in reversed(pl):
    print("▶", song)
Free bonus: Once you implement __getitem__ and __len__, Python gives your object support for slicing, reversed(), and the legacy iteration protocol for free — even without __iter__. Implementing __iter__ is still preferred because it's explicit and works correctly for objects where __getitem__ doesn't do simple integer indexing.

When to Implement Which Container Methods

  • __len__ — if len(obj) should return something meaningful. Skip it if "length" isn't well-defined for your object.
  • __getitem__ — if obj[i] should work. For collections, this is almost always worth implementing.
  • __setitem__ — only for mutable containers. Skip for immutable types like tuple-like classes.
  • __contains__ — if x in obj has a natural meaning. Python will fall back to iterating with __iter__, but implementing __contains__ directly can be much faster.
  • __iter__ — if the object should be loopable. If you only have __getitem__, Python's fallback works but is slower and doesn't work for non-integer-keyed collections.
Pitfall: Mutable default arguments

Notice def __init__(self, songs=None) — not def __init__(self, songs=[]). A mutable default argument is evaluated once and shared across all calls, so all instances end up pointing at the same list. This is one of the most common Python bugs, and it shows up frequently in container classes.

Part 6

Context Managers: __enter__ / __exit__

Any object that implements these two methods can be used in a with statement. __enter__ runs at the start of the block; __exit__ runs at the end — even if an exception was raised — which makes them ideal for cleanup code. Files, database connections, locks, and temporary directory changes are all traditionally managed this way.

python 
class Timer:
    def __init__(self, label="elapsed"):
        self.label = label

    def __enter__(self):
        import time
        self._start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc_val, tb):
        import time
        duration = time.perf_counter() - self._start
        print(f"{self.label}: {duration:.4f}s")
        return False


with Timer("loop") as t:
    total = sum(i * i for i in range(100000))
    print("total:", total)
The __exit__ signature is fixed: (self, exc_type, exc_val, tb). If no exception occurred, all three are None. Return True to suppress the exception (rarely what you want); return False or None to let it propagate normally.

The Easier Alternative: contextlib.contextmanager

For simple context managers, you don't need to write a class at all. Decorate a generator that yields once, and Python wraps it in the protocol for you:

python 
from contextlib import contextmanager
import time

@contextmanager
def timer(label="elapsed"):
    start = time.perf_counter()
    yield
    duration = time.perf_counter() - start
    print(f"{label}: {duration:.4f}s")


with timer("loop"):
    total = sum(i * i for i in range(100000))
    print("total:", total)

Use the class form when you need to subclass, add state, or reuse the manager across many with blocks. Use @contextmanager when the logic is short and self-contained. Both are idiomatic; knowing the underlying protocol is important because the decorator is just a convenience wrapper around the two dunder methods.

Async Context Managers

In async code, the equivalent pair is __aenter__ and __aexit__, used with async with. The pattern is identical, but the methods are async def. You'll see these in libraries like aiohttp and asyncpg, where entering a session is itself an I/O operation.

Part 7

Callable Objects: __call__

Implementing __call__ makes instances callable like functions. This is how you build stateful "functions" — objects that remember configuration between calls. It's a pattern you'll see in machine learning libraries (a trained model is called on new data), in rule engines, and in decorator factories.

python 
class Multiplier:
    def __init__(self, factor):
        self.factor = factor

    def __call__(self, x):
        return x * self.factor


double = Multiplier(2)
triple = Multiplier(3)

print(double(5))
print(triple(5))
print(callable(double))

numbers = [1, 2, 3, 4]
print(list(map(double, numbers)))

When to Prefer __call__ Over a Closure

Closures are simpler and usually preferred for small, one-off functions. Use __call__ when:

  • You need multiple methods alongside the call behavior (e.g., model.predict() AND model(x)).
  • You want to subclass or compose the callable.
  • You want introspection — the object appears in dir() with its own class and docstring.
  • The object is long-lived and represents an ongoing process (a trained model, a compiled query).

Otherwise, a function or a functools.partial is usually clearer.

Best Practices

Common Pitfalls and Best Practices

Dunder methods are powerful, but misuse is common. These are the pitfalls that show up most often in code review.

Pitfall 1: Calling dunder methods directly

Writing obj.__len__() is wrong, even though it "works". Use len(obj). The builtin understands type negotiation and will handle subclasses correctly. The same rule applies to obj.__str__() (use str(obj)), obj.__add__(x) (use obj + x), and every other dunder.

Pitfall 2: Returning the wrong type

__len__ must return an int, __bool__ must return a bool, __hash__ must return an int, and __str__ / __repr__ must return a str. Python enforces some of these (returning the wrong type raises TypeError), but you can get confusing errors if you return the wrong thing from __hash__ or __eq__.

Pitfall 3: Implementing every dunder

Don't. Implement only the ones that match your class's semantics. A User object shouldn't support +. A Configuration object shouldn't be iterable unless iterating configs means something. Overloading operators in ways that aren't obvious makes code harder to read, not easier.

Pitfall 4: Forgetting to handle NotImplemented

In __eq__, __lt__, __add__, and friends, always check isinstance against the expected type and return NotImplemented for unknown types. Otherwise your operators will raise AttributeError inside comparisons, breaking sorted(), in, and other builtins in subtle ways.

Pitfall 5: Mutating in __eq__

Comparison should be free of side effects. If a == b modifies either object, you'll eventually create very hard-to-debug issues — particularly with caching, logging, or set/dict lookups. Keep comparison pure.

Use dataclasses when you can. For simple value classes, @dataclass generates __init__, __repr__, and __eq__ for you. Adding frozen=True makes instances hashable and immutable. This is often better than writing the dunders by hand. You'll still need to implement dunders manually when you want custom behavior, but "just a bag of fields" classes should use the decorator.
Document your dunders. If + does something non-obvious — like concatenating two ranges, or merging two configs — write a docstring on __add__ explaining the semantics. Users of your class can't see through the syntax to guess what it does, and a five-line docstring prevents hours of confusion.
In the Wild

How Real Libraries Use Dunder Methods

Understanding dunders deepens immediately when you see how widely they're used. These examples from well-known libraries show the patterns in action.

NumPy arrays

NumPy's ndarray implements __add__, __mul__, __matmul__, __getitem__ (with slicing and fancy indexing), __len__, and many others. This is why arr[1:3] * 2 + arr[2:4] works as naturally as arithmetic on scalars.

__add____mul____matmul____getitem____len__
Pandas DataFrames

Pandas relies heavily on __getitem__ for column access (df["col"]), __setitem__ for assignment, and __repr__ to pretty-print tables in notebooks. __contains__ enables "col" in df.

__getitem____setitem____repr____contains____len__
PyTorch tensors

PyTorch tensors overload arithmetic operators (__add__, __mul__) to support GPU-accelerated element-wise math. They also implement __getitem__ for slicing, and __call__ on nn.Module so that model(x) is valid.

__add____mul____getitem____call__
Django QuerySets

Django QuerySets are lazy and chainable. They implement __iter__ for iteration, __getitem__ for indexing and slicing, and __len__ for counting — so you can write for post in Post.objects.all() and Post.objects.all()[0] without thinking about what's underneath.

__iter____getitem____len__
threading.Lock

The standard library's Lock object is a context manager: with lock: ... acquires the lock and releases it automatically — even on exception. This relies entirely on __enter__ and __exit__.

__enter____exit__

FAQ

Frequently Asked Questions

What's the difference between __init__ and __new__?
__new__ creates the instance (allocates it); __init__ configures it after creation. You almost never need __new__ except when subclassing immutable types like tuple, str, or int, or when implementing singletons and metaclasses. For the vast majority of classes, only __init__ is needed.
Why does defining __eq__ break my class in sets/dicts?
When Python sees __eq__ on a class, it sets __hash__ = None by default, which makes instances unhashable. Fix this by defining __hash__ too — typically return hash((self.attr1, self.attr2, …)) using the same fields your __eq__ compares. Alternatively, make the class immutable (e.g., frozen=True on a dataclass) and let Python's automatic hash handle it.
Do I always need to implement __iter__ to loop over an object?
No — if you implement __getitem__ with integer indices and raise IndexError when the index goes out of range, Python's legacy iteration protocol handles for loops automatically. That said, implementing __iter__ explicitly is clearer, faster, and less error-prone — especially for collections keyed by non-integers.
Should I return NotImplemented or raise from arithmetic dunders?
Return NotImplemented when the type is wrong (unknown operand). Raise exceptions for values that are invalid for that type (e.g., division by zero in __truediv__, or mismatched currencies in the comparison example above). This gives Python a chance to try the other operand's reflected method before deciding the operation isn't supported.
Can I override dunders at instance level?
No, and this surprises people coming from JavaScript. Python looks up dunders on the type, not the instance. So obj.__len__ = lambda: 5 won't affect len(obj). This is a deliberate design choice that keeps objects efficient and predictable — but it means you can't monkey-patch instance behavior the way you might in other languages.
Are dunders slower than regular methods?
No — dunders are actually faster when using the built-in syntax, because CPython's bytecode has fast paths for them. len(obj) is faster than obj.length() in most cases. The only thing to avoid is calling dunders directly (obj.__len__()), which bypasses the fast path.
Where can I see Python's exact specification of these?
See the official docs: Python Data Model — the definitive reference. For quick lookup, run dir(object) in a REPL: every dunder starts with __. You can also read the operator module docs, which map each operator to its dunder method.
