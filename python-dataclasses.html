Python Dataclasses
Skip the boilerplate, keep the power

A dataclass is a normal class where Python writes the repetitive methods for you. Declare the fields, add @dataclass, and you get __init__, __repr__, and __eq__ for free, plus optional ordering, hashing, immutability, and memory savings. This lesson explains the idea from scratch and walks through 16 runnable programs, each one explained line by line.

📖 Welcome: Why Dataclasses Matter

🤔 The big idea

Think about the classes you have written that mostly store values: a Student with a name and grade, an Order with items, a Point with two coordinates. Each one needs an __init__ that copies arguments into attributes, a __repr__ so printing is readable, and an __eq__ so two equal objects compare equal. That is the same code over and over, and every time you add a field you must update three methods.

A dataclass removes that work. You list the fields with type annotations, and the @dataclass decorator (in the standard-library dataclasses module since Python 3.7) generates the methods from that list. Add a field in one place and everything stays in sync.

💡 A dataclass is still a completely normal class. You can add your own methods, properties, class variables, and inheritance. The decorator only adds methods; it does not use a special base class or metaclass.

🎯 What you will learn

  • ✓What @dataclass generates and when to use it
  • ✓How to declare fields, set defaults, and avoid the mutable-default trap
  • ✓How to fine-tune each field with field(): default_factory, repr, compare, init
  • ✓How to validate and compute values with __post_init__ and InitVar
  • ✓How ordering, sorting, and hashing work (and why frozen matters)
  • ✓How to copy with replace() and convert with asdict() / astuple()
  • ✓How to use slots=True, kw_only=True, and inheritance
  • ✓How to avoid the most common mistakes

⚙️ How Dataclasses Actually Work

🔄 What @dataclass generates

When Python finishes building your class, the decorator reads the annotated names in order, treats them as fields, and adds methods to the class. By default you get:

Method addedSwitchWhat it does
__init__init=TrueTakes one parameter per field, assigns them
__repr__repr=TruePoint(x=1, y=2) style text
__eq__eq=TrueCompares all fields as a tuple
__lt__ __le__ __gt__ __ge__order=FalseSorting, only if you ask
__hash__depends on eq, frozenSee the hashing table in Lesson 5
__setattr__ / __delattr__frozen=FalseRaise an error, only when frozen
__match_args__match_args=TrueLets dataclasses work in match statements

📜 Five golden rules

  • 1Annotate every field. A name without an annotation is a plain class attribute, not a field.
  • 2Required fields first. Fields with defaults must come after fields without.
  • 3Use default_factory for lists, dicts, and sets. Never write = [].
  • 4Validate in __post_init__. Then every object is checked in one place.
  • 5Prefer frozen=True for value-like data. Immutable objects are safer and can be dictionary keys.
💡 Annotations are not type checks at runtime. Point("a", "b") runs. Use an editor or a checker such as mypy to catch type mistakes before running.

🆚 Dataclass, namedtuple, or plain class?

NeedBest choice
Mutable record with defaults and validation@dataclass
Immutable record, can be a dict key@dataclass(frozen=True)
Tiny immutable tuple that must also unpacknamedtuple / typing.NamedTuple
Rich behavior, little stored dataPlain class
Parse and validate untrusted input (JSON from the web)A validation library such as Pydantic

Lesson 2

🎛️ Fields, Defaults and default_factory Beginner

Fields work like function parameters. A field without a default is required; a field with = value is optional. Two rules to remember:

  • Fields without defaults must come before fields with defaults (same rule as function parameters).
  • Lists, dicts, and sets cannot be written directly as defaults. Use field(default_factory=...).

Lesson 5

⚖️ Ordering, Sorting and Hashing Intermediate

By default a dataclass compares with == but not with <. Switch on order=True to sort. Hashing follows a rule you should memorize:

eqfrozenResult for __hash__
True (default)False (default)Set to None: unhashable
TrueTrueGenerated from the fields: hashable
FalseanyInherited from object (identity)

The reason: a mutable object whose hash can change would get lost inside a set. This is the same lesson as __eq__ and __hash__ in the Dunder Methods page.
