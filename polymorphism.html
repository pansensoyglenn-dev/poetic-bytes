Polymorphism —
One Interface,
Many Forms.

You call shape.area() on a circle, a rectangle and a triangle — and each one answers in its own way. You call len() on a string, a list and your own class — and it just works. That is polymorphism: the same call, different behavior, chosen by the object receiving it.

This guide teaches all four flavors Python offers — method overriding, duck typing, operator overloading, and single dispatch — with runnable code, deep-dive walkthroughs, six exercises, a live lab, and 10 live app projects that put it all to work.

01 — The Idea

What Is Polymorphism?

🌀 Same Message, Different Behavior

The word comes from Greek: poly (many) and morph (form). In code it means one call site can work with many kinds of objects, and each object decides what the call actually does.

It is the pillar that makes the other three pay off. Encapsulation protects an object's data, abstraction defines the contract, inheritance shares code — and polymorphism lets callers use the contract without caring who is behind it.

Every Python example below is interactive: copy it, or press Run to execute it in your browser with Pyodide. Then try the live lab and explore the 10 live projects that use these same ideas.

The Problem It Solves

Without polymorphism, code asks "what are you?" before every action — an if / elif ladder on type, repeated in every function that touches the objects. Each new type means hunting down every ladder and editing it.

def area(shape):
    if shape.kind == "circle":
        return 3.14159 * shape.r ** 2
    elif shape.kind == "rectangle":
        return shape.w * shape.h
    # add "triangle"?  edit this function... and perimeter()... and draw()...

Smell: the same if kind == ... ladder appears in several functions. Behavior that belongs to the object has leaked out into the callers.

Goal: write the loop once — for s in shapes: s.area() — and add new shapes by writing new classes, touching nothing else.

A 30-Second Experiment: Watch Python Choose

Three classes in a chain. Only A and C define hello. Predict what each object prints before pressing Run.

class A:
    def hello(self):
        return "A.hello"

class B(A):
    pass

class C(B):
    def hello(self):
        return "C.hello"

for obj in (A(), B(), C()):
    print(type(obj).__name__, "→", obj.hello())

print([cls.__name__ for cls in C.__mro__])
print(B.hello is A.hello, C.hello is A.hello)
Expected output
A → A.hello B → A.hello C → C.hello ['C', 'B', 'A', 'object'] True False
📝 How to read this
  1. Python searches the MRO in order. For B().hello() it checks B (nothing), then A (found). For C().hello() it stops at C — the override wins.
  2. The loop never changes. obj.hello() is one expression that ran two different functions. That is polymorphism in its smallest form.
  3. The last line proves it with identity checks: B.hello is A.hello is True (inherited, same function object), while C.hello is A.hello is False (overridden).

03 — The Landscape

The Four Flavors of Polymorphism in Python

Python does not have one polymorphism feature — it has four tools that solve slightly different problems. Knowing which one fits is half the skill.

Which Tool, When?

FlavorHow it worksUse it when…Program
🧬 Method overridingSubclasses replace an inherited method; Python dispatches on the real type.Types share a family and some shared code.Program 1
🦆 Duck typingAny object with the right methods works. No base class needed.Unrelated types should plug into the same function.Program 2
➕ Operator overloadingDunder methods hook your class into +, ==, len(), for, …Your objects behave like numbers, collections or values.Programs 3–4
🎯 Single dispatch@singledispatch picks a function by the first argument's type.You can't add methods (built-ins, third-party types) but need per-type behavior.Program 4

Python has no classic overloading. In Java you can write area(int) and area(String) side by side. In Python, defining a function twice just rebinds the name — the second silently replaces the first. Default arguments, duck typing, or singledispatch do that job instead.

Rule of thumb: start with duck typing (simplest). Reach for inheritance when types genuinely share code. Add a Protocol or ABC when you want the contract written down and checked.

Five Programs, Explained Line by Line

Program 1 — Method Overriding: A Family of Shapes

The classic form. A base class defines what a shape can do; each subclass overrides how. Notice that describe() is written once, in the base class, yet prints a different area for each shape.

import math

class Shape:
    def __init__(self, name):
        self.name = name

    def area(self):
        raise NotImplementedError("Subclasses must implement area()")

    def describe(self):
        return f"{self.name}: area = {self.area():.2f}"

class Circle(Shape):
    def __init__(self, radius):
        super().__init__("Circle")
        self.radius = radius

    def area(self):
        return math.pi * self.radius ** 2

class Rectangle(Shape):
    def __init__(self, width, height, name="Rectangle"):
        super().__init__(name)
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height

class Square(Rectangle):
    def __init__(self, side):
        super().__init__(side, side, name="Square")

class Blob(Shape):
    pass

shapes = [Circle(2), Rectangle(3, 4), Square(5)]
for shape in shapes:
    print(shape.describe())

print(f"Total area: {sum(s.area() for s in shapes):.2f}")

try:
    Blob("Blob").describe()
except NotImplementedError as err:
    print("NotImplementedError:", err)
Expected output
Circle: area = 12.57 Rectangle: area = 12.00 Square: area = 25.00 Total area: 49.57 NotImplementedError: Subclasses must implement area()

🔍 Deep dive — how describe() finds the right area()

Follow one call: Square(5).describe(). The key is that Python restarts its search from the object's real class every time it sees self.something.

#What Python doesResult
1Looks for describe on SquareNot there.
2Moves up the MRO to RectangleNot there either.
3Moves up to ShapeFound — runs Shape.describe with self = the square.
4Inside it, self.area() — search restarts at SquareNot on Square; found on Rectangle.
5Rectangle.area runs: 5 * 525 → formatted as 25.00.

Why this matters: base-class code can call methods that don't exist yet in any subclass. Shape.describe was written before Square existed — and still works for it. This is the heart of the Template Method idea.

📖 Line-by-line walkthrough

  1. class Shape: with __init__(self, name) — stores a label every shape needs. Shared state lives once, in the parent.
  2. area() raises NotImplementedError — a placeholder that says "subclasses must override me". It is a plain class (no ABC), so you can still create a Shape; the error only fires when area() is called. For enforcement at creation time, use an abstract base class (see the Abstraction guide).
  3. describe() — the shared, polymorphic method. {self.area():.2f} calls whichever area the object has and formats it to two decimals.
  4. Circle.__init__ and super().__init__("Circle") — the subclass sets its own data (radius) and delegates the shared part to the parent. Skipping super() would leave self.name unset.
  5. Circle.area = math.pi * r ** 2 — the override. Same name and signature as the parent's, different behavior.
  6. Rectangle(width, height, name="Rectangle") — the extra name parameter has a default so a subclass can relabel it. This is what lets Square reuse the class cleanly.
  7. Square(Rectangle) — overrides nothing except the constructor: it calls super().__init__(side, side, name="Square"). A square is a rectangle with equal sides, so it inherits area() as-is. Overriding is optional.
  8. class Blob(Shape): pass — a subclass that forgot to override. It exists to demonstrate the failure path.
  9. shapes = [Circle(2), Rectangle(3, 4), Square(5)] — a list holding three different classes. That works because they all promise the same interface.
  10. The for loop — one line, shape.describe(), three behaviors. No isinstance, no if.
  11. sum(s.area() for s in shapes) — a generator expression calling area() polymorphically: 12.57 + 12 + 25 = 49.57.
  12. The final try / except — Blob("Blob").describe() reaches Shape.area, which raises. We catch NotImplementedError and print its message.

⚠️ Common mistakes

Mixing up NotImplementedError and NotImplemented. The first is an exception you raise in placeholder methods. The second is a sentinel value you return from operator methods (Program 3). Different jobs, confusingly similar names.

Changing the signature in an override. If Circle.area(self, precision) demands an extra argument, every caller that treats shapes uniformly — s.area() — breaks. Overrides must stay call-compatible with the parent.

Forgetting super().__init__(). The object builds fine, then describe() fails with AttributeError: 'Circle' object has no attribute 'name'.

Program 2 — Duck Typing: Unrelated Classes, One Function

Duck, Dog and Robot share no base class. make_noise() doesn't care — it only needs .speak() to exist. "If it walks like a duck and quacks like a duck, it's a duck."

from typing import Protocol, runtime_checkable

class Duck:
    def speak(self):
        return "Quack"

class Dog:
    def speak(self):
        return "Woof"

class Robot:
    def speak(self):
        return "Beep boop"

class Rock:
    pass

def make_noise(thing):
    return thing.speak()

for thing in [Duck(), Dog(), Robot()]:
    print(type(thing).__name__, "→", make_noise(thing))

try:
    make_noise(Rock())
except AttributeError as err:
    print("AttributeError:", err)

def safe_noise(thing):
    try:
        return thing.speak()
    except AttributeError:
        return "(silence)"

print(safe_noise(Rock()))

@runtime_checkable
class Speaker(Protocol):
    def speak(self) -> str:
        ...

print(isinstance(Duck(), Speaker), isinstance(Rock(), Speaker))
Expected output
Duck → Quack Dog → Woof Robot → Beep boop AttributeError: 'Rock' object has no attribute 'speak' (silence) True False

🔍 Deep dive — nominal vs structural typing

Inheritance-basedDuck typing
Question asked"Are you a Shape?""Can you .speak()?"
Needs a shared parentYesNo
Checked whenAt class definition (ABC) or call timeOnly when the method is actually called
Great forFamilies with shared codePlugging unrelated or third-party types together
RiskDeep hierarchies get rigidA missing method fails late, at runtime

You already use this daily. print(x, file=f) works with any object that has a write() method — a real file, io.StringIO, or your own class. Exercise 3 builds exactly that.

📖 Line-by-line walkthrough

  1. Duck, Dog, Robot — three independent classes (each inherits only from object) with the same method name. Their only link is a promise made by convention.
  2. class Rock: pass — deliberately has no speak. It is the control case.
  3. make_noise(thing) — just return thing.speak(). No type annotation, no isinstance. The function trusts the caller.
  4. The first loop — type(thing).__name__ prints each class name; make_noise works unchanged for all three.
  5. make_noise(Rock()) inside try — the failure surfaces as AttributeError: 'Rock' object has no attribute 'speak'. Python only discovers the problem at the moment of the call.
  6. safe_noise() — the EAFP style: try the call and handle the failure, instead of checking first. The try block contains only the one risky line so unrelated bugs aren't swallowed.
  7. @runtime_checkable + class Speaker(Protocol) — a Protocol writes the duck-typing contract down: "anything with speak() -> str". The ... body is intentional; protocols describe shape, not behavior.
  8. isinstance(Duck(), Speaker) — normally isinstance checks inheritance, but @runtime_checkable makes it check "does this object have a speak attribute?" So Duck → True although it never inherited from Speaker, and Rock → False.

⚠️ Common mistakes

Wrapping too much in try / except AttributeError. If the speak() method itself has a typo that raises AttributeError, a broad handler hides your bug and reports "(silence)". Keep the try body tiny.

Assuming runtime_checkable checks signatures. It only checks that the name exists, not its arguments or return type. Static tools like mypy check more.

Same name, different meaning. A Gun.shoot() and a Camera.shoot() both "work" with a function that calls .shoot() — duck typing can't tell you the semantics match. Name methods carefully.

Program 3 — Operator Overloading: A Money Type

Python turns a + b into a.__add__(b). By defining dunder methods, your own class gets natural syntax — and works with built-ins like sorted(), max() and sum().

from functools import total_ordering

@total_ordering
class Money:
    def __init__(self, amount, currency="PHP"):
        self.amount = round(amount, 2)
        self.currency = currency

    def _check(self, other):
        if other.currency != self.currency:
            raise ValueError("Currency mismatch")

    def __add__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        self._check(other)
        return Money(self.amount + other.amount, self.currency)

    def __mul__(self, factor):
        if not isinstance(factor, (int, float)):
            return NotImplemented
        return Money(self.amount * factor, self.currency)

    __rmul__ = __mul__

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return (self.amount, self.currency) == (other.amount, other.currency)

    def __lt__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        self._check(other)
        return self.amount < other.amount

    def __hash__(self):
        return hash((self.amount, self.currency))

    def __repr__(self):
        return f"Money({self.amount}, {self.currency!r})"

    def __str__(self):
        return f"{self.currency} {self.amount:,.2f}"

price = Money(120.50)
tax = Money(14.46)
print(price + tax)
print(price * 3)
print(2 * price)
print(sorted([Money(30), Money(5), Money(12.5)]))
print(max(Money(30), Money(5)))
print(Money(10) == Money(10.0))
print(sum([Money(1), Money(2)], Money(0)))

try:
    price + 5
except TypeError as err:
    print("TypeError:", err)

try:
    Money(1) + Money(1, "USD")
except ValueError as err:
    print("ValueError:", err)
Expected output
PHP 134.96 PHP 361.50 PHP 241.00 [Money(5, 'PHP'), Money(12.5, 'PHP'), Money(30, 'PHP')] PHP 30.00 True PHP 3.00 TypeError: unsupported operand type(s) for +: 'Money' and 'int' ValueError: Currency mismatch

🔍 Deep dive — how Python translates each expression

You writePython actually triesOutcome
price + taxprice.__add__(tax)Both are Money → new Money.

2 * price① int.__mul__(2, price) → NotImplemented

② int.__radd__(5, price) → NotImplemented		Both sides declined → Python raises TypeError.

Why return NotImplemented instead of raising TypeError? Returning it is a polite "not my job" that lets Python give the other operand a chance (the reflected method). If you raise TypeError yourself, you block that second chance — and break cooperation with other classes.

📖 Line-by-line walkthrough

  1. @total_ordering — a decorator from functools. You write __eq__ and __lt__; it fills in __le__, __gt__, __ge__.
  2. __init__ rounds to 2 decimals — keeps display tidy. (Real money code should use decimal.Decimal to avoid binary floating-point surprises; floats keep this lesson simple.)
  3. _check(self, other) — a private helper shared by __add__ and __lt__: mixing currencies raises a clear ValueError. Shared guards keep operators consistent.
  4. __add__ — first isinstance(other, Money); if not, return NotImplemented. Then check currency and return a new Money. Operators should not mutate their operands.
  5. __mul__ — accepts int or float only. Money * Money makes no sense, so it declines with NotImplemented.
  6. __rmul__ = __mul__ — multiplication is commutative here, so the reflected version simply reuses the same function. That makes 2 * price work.
  7. __eq__ — compares (amount, currency) tuples. Money(10) == Money(10.0) is True because both amounts equal ten and both use PHP.
  8. __lt__ — the one ordering primitive @total_ordering needs.
  9. __hash__ — defining __eq__ silently sets __hash__ to None, making objects unhashable. We restore it using the same fields as __eq__: equal objects must have equal hashes.
  10. __repr__ vs __str__ — repr is for developers (shown inside the sorted list: Money(5, 'PHP')); str is for users (PHP 134.96). print(x) uses __str__; lists use __repr__ for their items.
  11. The demo lines — 120.50 + 14.46 = 134.96; price * 3 = 361.50; 2 * price = 241.00; sorted and max use __lt__; sum with a Money(0) start gives 3.00.
  12. The two error cases — price + 5 ends in a standard TypeError that Python itself builds; Money(1) + Money(1, "USD") hits our own ValueError.

⚠️ Common mistakes

Raising TypeError inside __add__. It breaks the reflected-operand protocol. Return NotImplemented and let Python decide.

Defining __eq__ without __hash__. Using the object in a set then fails with TypeError: unhashable type.

Mutating in __add__. If a + b changes a, surprises follow. Return a new object. (In-place behavior belongs to __iadd__ for +=.)

Surprising operators. A + that sends an email would be legal but unreadable. Overload an operator only when its meaning is obvious.

Program 4 — Built-in Polymorphism and Single Dispatch

Polymorphism is everywhere in Python's built-ins: len(), +, *, for, in. This program shows how, then adds your own class to the club and uses @singledispatch for per-type behavior you can't add as methods.

from functools import singledispatch

print(len("poetic"), len([1, 2, 3]), len({"a": 1}), len(range(10)))
print(1 + 2, "a" + "b", [1] + [2], (1,) + (2,))
print(3 * 2, "ab" * 3, [0] * 3)

class Playlist:
    def __init__(self, *songs):
        self._songs = list(songs)

    def __len__(self):
        return len(self._songs)

    def __iter__(self):
        return iter(self._songs)

mix = Playlist("Sunrise", "Tides", "Harbor")
print(len(mix), list(mix), "Tides" in mix, sorted(mix))

@singledispatch
def describe(value):
    return f"Something else: {value!r}"

@describe.register
def _(value: int):
    kind = "even" if value % 2 == 0 else "odd"
    return f"Integer {value} ({kind})"

@describe.register
def _(value: str):
    return f"Text with {len(value)} characters"

@describe.register(list)
def _(value):
    return f"List of {len(value)} items"

for item in [7, "poetic", [1, 2, 3], 3.5, None, True]:
    print(describe(item))
Expected output
6 3 1 10 3 ab [1, 2] (1, 2) 6 ababab [0, 0, 0] 3 ['Sunrise', 'Tides', 'Harbor'] True ['Harbor', 'Sunrise', 'Tides'] Integer 7 (odd) Text with 6 characters List of 3 items Something else: 3.5 Something else: None Integer True (odd)

The idea: built-in functions don't know your class. They call agreed-upon dunder hooks. Implement the hook, and your class joins the same polymorphic club as str, list and dict.

📖 Line-by-line walkthrough

  1. len(...) on four types — a string, list, dict and range all answer len() differently (6, 3, 1, 10). One function name, four implementations.
  2. + on numbers, strings, lists, tuples — addition, concatenation, list joining, tuple joining: 3, ab, [1, 2], (1, 2). Same symbol, type-specific meaning.
  3. * on number, string, list — multiply, repeat, repeat: 6, ababab, [0, 0, 0].
  4. Playlist.__init__(self, *songs) — *songs collects any number of positional arguments into a tuple; we store them as a list in _songs (underscore = internal).
  5. __len__ — returns the count. That alone makes len(mix) work and also makes an empty playlist falsy in if mix:.
  6. __iter__ — returns an iterator over the songs. This one method powers list(mix), for song in mix, "Tides" in mix (via fallback iteration) and sorted(mix).
  7. print(len(mix), list(mix), "Tides" in mix, sorted(mix)) — four built-ins, one class, zero extra code. sorted returns a new alphabetical list.
  8. @singledispatch def describe(value) — the base function is the fallback used for any unregistered type. {value!r} uses the repr of the value.
  9. @describe.register with a type annotation — registers the function below for the annotated type (int, then str). The function name _ is a convention for "I don't need this name".
  10. @describe.register(list) — the explicit form, passing the type as an argument. Use it when you can't or don't want to annotate.
  11. The final loop — each value is dispatched by its type: 7 → integer branch, "poetic" → text, the list → list, 3.5 and None → fallback.
  12. The last item, True — prints Integer True (odd)! bool is a subclass of int, and with no bool registration, Python dispatches to the closest ancestor that is registered. Surprising? Yes — and a perfect reminder that dispatch follows the MRO.

⚠️ Common mistakes

Forgetting bool is an int. Register bool separately if you need to treat it differently (Exercise 5 does).

Expecting dispatch on every argument. singledispatch looks only at the first argument. For methods inside a class, use singledispatchmethod.

Trying "overloading" by defining a function twice. The second def silently replaces the first — no error, no dispatch.

Program 5 — Refactoring: From isinstance Ladder to Polymorphism

The practical payoff. First, a fee calculator written as an if / elif ladder — which breaks the moment a new payment method (Maya) shows up. Then the same feature rebuilt with polymorphism, where adding Maya means one new class and zero edits elsewhere.

class Card:
    pass

class GCash:
    pass

class Cash:
    pass

def fee_ladder(method, amount):
    if isinstance(method, Card):
        return round(amount * 0.029 + 15, 2)
    elif isinstance(method, GCash):
        return round(amount * 0.02, 2)
    elif isinstance(method, Cash):
        return 0.0
    raise TypeError(f"No fee rule for {type(method).__name__}")

class Maya:
    pass

try:
    fee_ladder(Maya(), 1000)
except TypeError as err:
    print("Ladder failed:", err)

print("-" * 44)

class PaymentMethod:
    def fee(self, amount):
        raise NotImplementedError

    def checkout(self, amount):
        fee = self.fee(amount)
        name = type(self).__name__
        return f"{name:<14} total {amount + fee:>9,.2f} (fee {fee:,.2f})"

class CardPayment(PaymentMethod):
    def fee(self, amount):
        return round(amount * 0.029 + 15, 2)

class GCashPayment(PaymentMethod):
    def fee(self, amount):
        return round(amount * 0.02, 2)

class CashPayment(PaymentMethod):
    def fee(self, amount):
        return 0.0

class MayaPayment(PaymentMethod):
    def fee(self, amount):
        return round(amount * 0.015, 2)

for method in [CardPayment(), GCashPayment(), CashPayment(), MayaPayment()]:
    print(method.checkout(1000))
Expected output
Ladder failed: No fee rule for Maya -------------------------------------------- CardPayment total 1,044.00 (fee 44.00) GCashPayment total 1,020.00 (fee 20.00) CashPayment total 1,000.00 (fee 0.00) MayaPayment total 1,015.00 (fee 15.00)

🔍 Deep dive — what changes when a new type arrives

Task: support MayaLadder versionPolymorphic version
Files / functions to editfee_ladder — and every other ladder (receipts, refunds, reports…)None. Write MayaPayment.
Forget one spot?Silent wrong answer or late TypeErrorImpossible — the class carries its own behavior

This is the Open/Closed Principle: the system is open to extension (new classes) but closed to modification (no edits to working code).

📖 Line-by-line walkthrough

  1. Card, GCash, Cash (empty classes) — stand-ins that only exist to be tested with isinstance. They carry no behavior, which is the whole problem.
  2. fee_ladder — asks "what are you?" with isinstance three times, then raises TypeError for anything unknown. Fees: card 2.9% + 15, GCash 2%, cash free.
  3. class Maya: pass and the failing call — a brand-new method arrives. The ladder has no branch for it, so it prints Ladder failed: No fee rule for Maya. Fixing it means editing fee_ladder.
  4. print("-" * 44) — a divider. Here * repeats a string — Program 4's polymorphism, in the wild.
  5. PaymentMethod base class — declares fee() (placeholder) and implements checkout() once. checkout calls self.fee(amount), whichever class self is.
  6. The format spec {name:<14} and {amount + fee:>9,.2f} — <14 left-aligns in 14 characters, >9 right-aligns in 9, , adds thousands separators, .2f gives two decimals. That is what lines the columns up.
  7. CardPayment, GCashPayment, CashPayment — each overrides only fee(). Same fee rules as the ladder, now living inside the classes.
  8. MayaPayment — the "later" addition at 1.5%. Notice nothing above it changed.
  9. The final loop — method.checkout(1000) for four classes: totals 1,044.00, 1,020.00, 1,000.00 and 1,015.00. Maya worked instantly.

⚠️ When isinstance is still fine

At the boundary. Validating untrusted input (parsing JSON, checking a function argument) is a legitimate use of isinstance. The smell is a ladder that decides behavior for objects you control. Also note that operator methods in Program 3 use isinstance on purpose — to decide whether to return NotImplemented.

Over-engineering. Two types and one ladder used in one place? A plain if may be clearer. Polymorphism pays off as types and operations multiply.

Exercise 1 — Add a Triangle

Warm-up

Task: extend the shape family with Triangle(base, height) and find the shape with the biggest area using max() with a key function — without any isinstance.

Hint: copy the pattern of Circle: store the dimensions in __init__, override area(). The area is 0.5 * base * height.

Show solution & explanation 
import math

class Shape:
    def area(self):
        raise NotImplementedError

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        return math.pi * self.radius ** 2

class Triangle(Shape):
    def __init__(self, base, height):
        self.base = base
        self.height = height

    def area(self):
        return 0.5 * self.base * self.height

shapes = [Circle(1), Triangle(6, 5), Circle(2)]
for s in shapes:
    print(f"{type(s).__name__:<9} {s.area():6.2f}")

biggest = max(shapes, key=lambda s: s.area())
print("Biggest:", type(biggest).__name__)
Expected output
Circle 3.14 Triangle 15.00 Circle 12.57 Biggest: Triangle

max(shapes, key=lambda s: s.area()) calls area() on each shape polymorphically and returns the object with the largest result. Adding Triangle required no change to the loop or to max — that is polymorphism paying off.

Exercise 2 — A Vector2D Type

Easy

Task: write Vector2D(x, y) that supports +, -, multiplication by a number (both v * 2 and 2 * v), abs(v) for its length, ==, hashing, and a readable repr.

Hint: abs(v) calls __abs__. Use math.hypot(x, y) for the length. Return NotImplemented for unsupported operand types.

Show solution & explanation 
import math

class Vector2D:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __add__(self, other):
        if not isinstance(other, Vector2D):
            return NotImplemented
        return Vector2D(self.x + other.x, self.y + other.y)

    def __sub__(self, other):
        if not isinstance(other, Vector2D):
            return NotImplemented
        return Vector2D(self.x - other.x, self.y - other.y)

    def __mul__(self, k):
        if not isinstance(k, (int, float)):
            return NotImplemented
        return Vector2D(self.x * k, self.y * k)

    __rmul__ = __mul__

    def __abs__(self):
        return math.hypot(self.x, self.y)

    def __eq__(self, other):
        if not isinstance(other, Vector2D):
            return NotImplemented
        return (self.x, self.y) == (other.x, other.y)

    def __hash__(self):
        return hash((self.x, self.y))

    def __repr__(self):
        return f"Vector2D({self.x}, {self.y})"

a = Vector2D(3, 4)
b = Vector2D(1, 2)
print(a + b)
print(a - b)
print(a * 2)
print(2 * a)
print(abs(a))
print(a == Vector2D(3, 4))
print({a, Vector2D(3, 4)})
Expected output
Vector2D(4, 6) Vector2D(2, 2) Vector2D(6, 8) Vector2D(6, 8) 5.0 True {Vector2D(3, 4)}

The vector (3, 4) has length 5.0 — the classic 3-4-5 triangle. The set {a, Vector2D(3, 4)} contains just one element because the two vectors are equal and hash the same; that only works because we defined __hash__ alongside __eq__.

Exercise 3 — A Duck-Typed Logger

Easy

Task: write log(writer, message) that works with anything having a write(text) method. Test it with your own ConsoleWriter, your own in-memory ListWriter, and Python's built-in io.StringIO — three unrelated classes.

Hint: log should contain no isinstance and no mention of any writer class. Remember to end each message with "\n".

Show solution & explanation 
import io

class ConsoleWriter:
    def write(self, text):
        print(text, end="")

class ListWriter:
    def __init__(self):
        self.lines = []

    def write(self, text):
        self.lines.append(text)

def log(writer, message):
    writer.write(message + "\n")

memory = ListWriter()
buffer = io.StringIO()

for writer in (ConsoleWriter(), memory, buffer):
    log(writer, "server started")

print(memory.lines)
print(repr(buffer.getvalue()))
Expected output
server started ['server started\n'] 'server started\n'

The first line comes from ConsoleWriter; the next two show what landed in the other writers. io.StringIO was written by the Python core team years before your log function existed — yet it plugs in, because it honors the same informal interface. That is why duck typing makes libraries so composable.

Exercise 4 — Kill the Ladder

Medium

Task: refactor the shipping calculator below into polymorphic classes. Then add a Poster that costs a flat 5.0 to ship — without editing any existing class.

def shipping_cost(item):
    if item["kind"] == "book":
        return 3.0
    elif item["kind"] == "laptop":
        return 12.0 + item["weight"] * 1.5
    elif item["kind"] == "ebook":
        return 0.0
    raise ValueError("unknown kind")

cart = [
    {"kind": "book"},
    {"kind": "laptop", "weight": 2},
    {"kind": "ebook"},
]
print([shipping_cost(item) for item in cart])
print(sum(shipping_cost(item) for item in cart))

Hint: create an Item base class with shipping_cost(). Give each kind its own subclass; the laptop needs a weight attribute from its constructor.

Show solution & explanation 
class Item:
    def shipping_cost(self):
        raise NotImplementedError

class Book(Item):
    def shipping_cost(self):
        return 3.0

class Laptop(Item):
    def __init__(self, weight):
        self.weight = weight

    def shipping_cost(self):
        return 12.0 + self.weight * 1.5

class EBook(Item):
    def shipping_cost(self):
        return 0.0

class Poster(Item):
    def shipping_cost(self):
        return 5.0

cart = [Book(), Laptop(2), EBook(), Poster()]

Exercise 5 — A Recursive to_text

Medium

Task: using @singledispatch, write to_text(value) that turns nested data into readable text: booleans become yes / no, lists become [a, b], dicts become {key: value}, and everything else uses str(). It must handle nesting.

Hint: register bool separately (it is a subclass of int!). Inside the list and dict versions, call to_text again on each element — dispatch happens at every level.

Show solution & explanation 
from functools import singledispatch

@singledispatch
def to_text(value):
    return str(value)

@to_text.register
def _(value: bool):
    return "yes" if value else "no"

@to_text.register
def _(value: list):
    return "[" + ", ".join(to_text(v) for v in value) + "]"

@to_text.register
def _(value: dict):
    pairs = (f"{k}: {to_text(v)}" for k, v in value.items())
    return "{" + ", ".join(pairs) + "}"

data = {"name": "Ana", "active": True, "scores": [90, 85.5, False]}
print(to_text(data))
Expected output
{name: Ana, active: yes, scores: [90, 85.5, no]}

Trace "active": True: the dict version calls to_text(True), dispatch finds the bool registration, so we get yes. The number 90 falls to the base function, str(90). Because we registered bool explicitly, False inside the list also becomes no instead of 0.

Exercise 6 — Debug the Broken Temperature

Medium

Task: the program below has several bugs. Run it, read each error, fix it, and run again until all three lines print sensible results: a sorted list that shows readable values, False for comparing with a plain number, and a set with one element. Expect more than one bug.

class Temperature:
    def __init__(self, degrees):
        self.degrees = degrees

    def __eq__(self, other):
        return self.degrees == other.degrees

temps = [Temperature(30), Temperature(12), Temperature(21)]
print(sorted(temps))
print(Temperature(5) == 5)
print(len({Temperature(5), Temperature(5)}))

Hint: the first error is TypeError: '<' not supported…. After fixing it, ask: what does the printed list look like? What happens when other is an int? What happens when you put the object in a set?

Show solution & explanation 
from functools import total_ordering

@total_ordering
class Temperature:
    def __init__(self, degrees):
        self.degrees = degrees

    def __eq__(self, other):
        if not isinstance(other, Temperature):
            return NotImplemented
        return self.degrees == other.degrees

    def __lt__(self, other):
        if not isinstance(other, Temperature):
            return NotImplemented
        return self.degrees < other.degrees

    def __hash__(self):
        return hash(self.degrees)

    def __repr__(self):
        return f"Temperature({self.degrees})"

temps = [Temperature(30), Temperature(12), Temperature(21)]
print(sorted(temps))
print(Temperature(5) == 5)
print(len({Temperature(5), Temperature(5)}))
Expected output
[Temperature(12), Temperature(21), Temperature(30)] False 1

Bug 1: no __lt__, so sorted() raised TypeError. Bug 2: no __repr__, so the list would print <__main__.Temperature object at 0x…>. Bug 3: __eq__ assumed other had .degrees, so Temperature(5) == 5 raised AttributeError; returning NotImplemented lets Python fall back to "not equal". Bug 4: defining __eq__ removed __hash__, so the set raised TypeError: unhashable type.

Where Polymorphism Shows Up

Polymorphism is the engine behind most classic design patterns and everyday Python libraries.

♟️

Strategy

Swap algorithms (fee rules, sorting keys, pricing) behind one method name. Program 5 is a Strategy in disguise.

📐

Template Method

A base method fixes the steps and calls overridable hooks. describe() and checkout() both work this way.

🔌

Plugins & Adapters

Any object with the right methods plugs in — payment gateways, storage backends, notification channels.

🧪

Test Doubles

A fake write() object replaces a real file in tests. Duck typing makes mocking easy.

📄

File-like Objects

Files, StringIO, sockets and HTTP responses all share read() / write(), so one function handles them all.

⚖️

Liskov Substitution

The rule that keeps polymorphism safe: a subclass must behave well anywhere its parent is accepted.

08 — Do's & Don'ts

Best Practices for Polymorphic Design

Habits That Keep It Safe

✓ DO: Keep overrides call-compatible. Same name, same parameters, same kind of return value. A caller using the parent type must not be surprised.

✓ DO: Call super() when extending. If you add behavior rather than replace it, delegate the shared part to the parent.

✓ DO: Return NotImplemented from operator methods when the other operand's type isn't supported.

✓ DO: Define __repr__ for every class. Debugging polymorphic collections is miserable when every item prints as <object at 0x…>.

✓ DO: Write the duck-typed contract down with a Protocol or a docstring, so other developers know what write() or speak() must do.

✗ DON'T: Build isinstance ladders to choose behavior. If you control the classes, move the behavior into them.

✗ DON'T: Override to change the meaning. A ReadOnlyList.append() that raises breaks every caller that expects a list. If a subclass can't honor the parent's promise, it probably shouldn't be a subclass (Liskov Substitution).

✗ DON'T: Wrap big blocks in except AttributeError. Duck-typing failures and genuine bugs look identical when the net is too wide.

✗ DON'T: Overload operators for unexpected meanings. + should add, combine or concatenate — not send, delete or save.

✗ DON'T: Forget the __eq__ / __hash__ pair. Equal objects must hash equally, or sets and dicts misbehave.

13 — The Road Ahead

Wrapping Up

🏁 What You've Learned

You met polymorphism in all four of its Python forms — overriding, duck typing, operator overloading and single dispatch — and saw the same payoff each time: callers stop asking "what are you?" and simply ask the object to do its job.

You also practiced the safety rules that keep it healthy: keep overrides compatible, return NotImplemented from operators, pair __eq__ with __hash__, and keep except blocks narrow. Write to the interface, not the implementation.

Key Takeaways

  • Polymorphism = one call, many behaviors — the receiving object decides what happens.
  • Overriding works through the MRO: Python searches from the object's real class upward.
  • Duck typing needs only matching method names — no shared parent — but fails late, so keep try blocks small.
  • Dunder methods make your classes work with +, ==, len(), for and sorted().
  • @singledispatch adds per-type behavior when you can't edit the class — remember bool is an int.
  • Replace isinstance ladders with methods, and new types arrive without touching old code.

✨ Four pillars, one idea: hide the details, share the contract, reuse the code — and let every object answer in its own voice.
